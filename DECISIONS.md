# DECISIONS.md — running decision log

Append-only. Format: date · decision · why. Newest at the bottom.

---

**2026-07-11 · API contract is Zod-only in `lib/api-contract`; OpenAPI and codegen are removed.**
Why: the orval toolchain (`orval@8.5.3` + `@scalar/json-magic@0.11.7`) is broken upstream and once destroyed its own generated output mid-run; the generated clients (`lib/api-zod`, `lib/api-client-react`) have been stale ever since and nothing in the app consumes them for the money endpoints anyway. One set of Zod schemas imported by both server (request+response validation in dev) and frontend (typed hooks) eliminates the generation step and the drift.

**2026-07-11 · Money is stored as integers in minor units (bigint columns); floats are banned from money math.**
Why: every current money column is `double precision`, which invites rounding drift across a 2,700-line float-based calculation engine. Integer minor units + decimal.js for rates/quantities make every sum exact and every comparison reliable. This is the foundation the whole ledger rewrite sits on.

**2026-07-11 · The ledger is append-only with frozen cost snapshots and effective-dated cost components.**
Why: today refunds link to originals only via loose metadata, transactions hard-delete (with stock side effects), and editing an item's cost silently rewrites historical profit. Append-only headers (`parent_transaction_id` for refunds/corrections, void as status), `cost_snapshot` frozen at line creation, and effective-dated CostComponents make historical numbers immutable and auditable — the property a "business doctor" product cannot function without.
**2026-07-12 · A `businesses` table scopes every money row; one business per user for now.**
Why: the old tables hung everything off Clerk's `user_id` string. The new core FKs every source/item/transaction to `businesses.id` (unique per user today), so multi-business later is a data change, not a schema rewrite. Services resolve it via `ensureBusiness(userId)`, which also guarantees the "Manual" source exists.

**2026-07-12 · R2 dropped the legacy money tables from the DATABASE while keeping their Drizzle definitions exported from `@workspace/db/legacy`.**
Why: phase isolation. The pre-rewrite api-server routes keep compiling (R3 replaces them); at runtime they fail with "relation does not exist", which is the accepted state listed in REWRITE_PLAN §7. Two clean generated migrations (0001 drops, 0002 creates) instead of one unreviewable ALTER soup. The legacy `.mjs` seeder and `seed:demo` scripts were deleted — they can never run again; `pnpm db:seed` (through domain services) replaces them.

**2026-07-12 · Ladder inclusion rules locked: pending and void are excluded; shipping charged counts as gross revenue; taxes collected never count.**
Why: the ladder is cash-basis — pending money hasn't arrived, void never existed. Shipping charged to a customer is a service the business sells (only taxes are pass-through). Refunds subtract in the period they occur. These rules live in exactly one place: `lib/domain/src/profit.ts`.

**2026-07-12 · `percent_of_subtotal` currently resolves per-unit against the unit price (same base as `percent_of_price`).**
Why: the snapshot format stores per-unit cents, and with no order-level fee engine yet the two bases are numerically identical. The calc types stay distinct so subtotal-based fees can diverge (e.g. discounted-base marketplace fees) without a schema change. Revisit when an integration needs it.

**2026-07-12 · Refund lines always carry a cost snapshot with `qty_basis`, even when nothing was recovered.**
Why: cumulative over-refund protection needs the refunded QUANTITY of prior refunds, and the refund line itself stores qty "1" × exact amount (so partial amounts never round). `qty_basis` in the snapshot is where that quantity survives persistence.

**2026-07-12 · R3 started early as a server-side bridge: the four legacy money endpoints now serve the NEW core in the OLD JSON shapes.**
Why: after R2 dropped the legacy tables the app was unusable (the owner hit spinners on every money page), and waiting for the full R3 prompt would have left it dead. `/api/data` (settings + empty legacy collections, seed/reset now drive the new core), `/api/offers` (revenue_items + the two bridge cost components "Product cost"/"Direct cost", cost edits effective-dated), `/api/expense-items` (new catalog; scheduling fields accepted-and-ignored until the recurring engine), `/api/transactions` (full ledger adapter). Floats exist ONLY at this serialization boundary (`lib/legacyAdapters.ts`, all marked TODO(R4): delete); storage and math stay integer cents. Ledger semantics are enforced honestly through the bridge: DELETE = void (rows persist, hidden from the API), changed amounts are rejected with a void-and-re-enter message, refunds require the original transaction and post as linked adjustments (flat amounts allocated across lines with exact decimal math), catalog deletes are archives. Backup import returns 501 until rebuilt. Known cosmetic gap: refund rows render as "Uncategorized" in the old table — R4's ledger UI replaces that page.

**2026-07-12 · api-server test files run serially (--test-concurrency=1).**
Why: the two integration suites share profit_loop_test; node's default per-file parallelism let one file TRUNCATE while the other seeded — a race that produced flaky failures. Serial execution costs under a second.

Why: all money is now server-computed integer cents behind typed `defineRoute` endpoints; the UI only formats. `services/read.ts` is the one read model (summaries, item stats, rollups, P&L ladder, Quick-Add preview) so every screen agrees, and the preview shares `resolveTransactionLines` with create so what you preview is exactly what's saved. Why: a Lifetimely-style catalog table reads clearest when margin reflects how the item sells and refund risk is its own column. Refunds still hit the period P&L (cash basis) and the ledger; they just don't muddy per-item margin. Logged so future edits don't "fix" it into double-counting.

**2026-07-13 · R4 landed the recurring engine, subscriptions, and People; `client_customers` became `people`.**
Why: People is cross-vertical (customers, vendors, employees) and had to own the `person_id` FK the ledger already carried. **2026-07-13 · Person metrics (lifetime revenue, true LTV, order count, active subs, vendor spend) are derived at query time, never stored.**
Why: they are projections of the append-only ledger + subscription events. Storing them would create a second source of truth that drifts after every refund, void, or merge. `services/analytics.ts` computes them on read; `mergePersons` repoints rows and archives the loser so the derivation stays correct without touching history.

**2026-07-13 · Recurring idempotency rides `unique(schedule_id, scheduled_for)`; a post catches 23505 and no-ops. Occurrences post at the SCHEDULED date, not the run date.**
Why: the job (cron or manual) must be safe to run twice, and catch-up after downtime must backfill each missed period at the date it was due so the P&L lands money in the right period. The anchor day is remembered, not degraded (Jan-31 → Feb-28/29 → Mar-31), and catch-up is capped at 12 occurrences with a UI warning so a long outage can't post a hundred rows silently.

**2026-07-13 · "This occurrence only" edits the one transaction; "this and future" end-dates the schedule at its last post and clones a new one. The subscription event stream is the MRR/churn dataset.**
Why: history is immutable — changing a plan price can never rewrite what already posted. End-date-and-clone keeps every past occurrence frozen while future ones use the new terms (and emits a `plan_changed` event). MRR, movement, churn, and NRR are all folded from `subscription_events` (created/activated/payment_posted/canceled…), so the numbers reconcile to an auditable log rather than a mutable counter.

**2026-07-13 · The R4 seed layer is deterministic by fixed relative-day posts, not by running the calendar engine.**
Why: the hand-computed P&L must stay exactly reproducible. Subscription payments and recurring-expense history are seeded as explicit transactions on pinned relative days, and every one-off cohort sale is placed >90 days back, so only in-window subscription revenue (Rs 1,050) and recurring expenses (Rs 2,560) move the 90-day ladder. The engine's own date math is proven separately by the domain + integration tests, not by the seed.

Why: creating a subscription/rental revenue item or a `recurring`-behavior expense fires a toast action ("Set up recurring →") into the full New-recurring dialog, which owns cadence/anchor/posting-mode/source. One schedule-creation surface instead of two divergent ones; the item dialogs stay simple.

**2026-07-25 · Revenue items become a tree: a catalog row may carry variants, and only the deepest level is sellable.**
Why (owner design, "shirt => black => medium => cotton"): owners think in options, not in a flat SKU list. `revenue_items.parent_id` self-references the same table (migration 0010), so a variant IS a revenue item — it inherits every column, every stat, every source link and cost component with no parallel structure. Nesting is unbounded because the owner asked for "and so on"; a node with children is stored price-less and `createTransaction` refuses to post against it ("has variants — record the sale against one of its variants"), which is what makes "only the last level is the actual sellable item" a database fact rather than a UI convention. Uniqueness moved from `unique(business_id, name)` to two partial indexes — unique among roots, and unique among siblings under one parent — so every item can have its own "Medium". Variants are create-time only for now; editing one is editing an ordinary revenue item.

**2026-07-25 · The form's single "direct cost" is sugar over ONE cost component named "Direct cost", never a column.**
Why: the owner wants one friendly cost number at creation with the richer costs handled per transaction later, but a mutable `cost` column would silently rewrite historical profit and break the effective-dating invariant. `setDirectCost` writes a `fixed_per_unit` CostComponent; `directCostCents` on the read model surfaces the open version back to the form. Editing it therefore closes a version and opens a successor like any other component, and frozen snapshots stay frozen. Percent-based fees keep their existing home under Advanced → other costs.

**2026-07-25 · The owner's "origin" field is the existing Sources layer, renamed "Where you sell it" in the UI, and it is multi-select.**
Why: the owner described saved, reusable, user-written origins ("outlet x", "client z") alongside fixed integration ones ("Shopify – store1") — which is exactly `sources` (user-named channels, `kind: "manual"` vs integration kinds, unique per business, "Manual" seeded by default). Building a second field would have forked the money path and broken per-source profit. Two deliberate deviations from the sketch: the word "origin" stays reserved for transaction `origin` (`manual | recurring_engine | integration | import`, surfaced as "Added From"), since conflating "how the row got created" with "where the money flowed" would poison both; and the field is multi-select via `revenue_item_sources`, because the owner's own goal ("services we sell on Fiverr PLUS on Upwork") requires one item on several channels. Typing a new channel creates a `manual` source inline.

**2026-07-25 · Type-conditional fields land as SKU (product) and billing cycle (subscription/rental); billing cycle is a DEFAULT, not a posting cadence.**
Why: the owner asked for "fields special to the revenue type". `default_billing_cycle` is validated server-side against the type and exists only to pre-fill a recurring schedule — the schedule still owns the cadence and its `unique(schedule_id, scheduled_for)` idempotency, so catalog rows still never move money. The list is daily/weekly/monthly/quarterly/yearly: the sketch's "hourly" is dropped (the recurrence engine has no such interval) and "quarterly" is added back (it does). Tiered pricing finally gets storage — an ordered `tiers_json` validated for increasing quantities with only the last tier open-ended — and the first tier becomes the item's base price so a zero-setup sale still resolves.

**2026-07-25 · Deferred from the owner's flowchart: barcode/inventory tracking and file attachments on catalog items.**
Why: inventory is stock, not money — it needs its own subsystem and must stay out of the ledger, so it is scoped separately rather than bolted on as two columns. Attachments already exist for transactions (`transaction_attachments`, MIME allowlist, 5MB cap); extending them to catalog items is a small follow-up, so the Advanced section ships with a text description now. The sketch's `royalty` type was kept (it exists today) even though the sketch omitted it, and per-item currency, unit label, notes, and archive status were kept for the same reason.

**2026-07-27 · Business type is a two-value enum (ecommerce | service) on the BUSINESS, gating features individually with owner overrides.**
Why (owner decision, expense module Phase 1): Profit Loop is cross-vertical, so ecommerce-shaped features (order outcomes, RTO, courier cost rules, COD fees) must be INVISIBLE to a freelancer, not merely disabled. `businesses.business_type` (migration 0011) rather than `user_settings` because it scopes money and seeding, and text rather than a Postgres enum so adding "retail"/"digital" later is a one-line change — both are deliberately deferred. The rule lives in `lib/domain/src/capabilities.ts` because BOTH the server (what to seed/compute) and the UI (what to render) ask it; two copies would drift. Gating is per-feature, not a master switch: `businesses.feature_overrides` is a jsonb map where an ABSENT key means "follow my type", so an explicit false stays distinguishable from never-chose and changing type later still moves the default for anyone who never expressed a preference. Writes merge, and a null value clears a key back to following the type (with a "reset" affordance in Settings). Unknown keys are rejected at the contract boundary and re-sanitized server-side so a stale client cannot widen access. `features` is server-resolved and read-only; clients patch `featureOverrides`.

**2026-07-27 · Business type chooses the SEEDED expense-type list only — never what a user may create.**
Why (owner decision): expense types stay fully user-created and unlimited for every business type. The type is a starting-point convenience (a freelancer should not be handed "COD fee"), not a permission system. Nothing in the gating layer may ever restrict catalog creation.

**2026-07-27 · Fixed-vs-variable is its own column (`expense_items.cost_nature`), and `type` is demoted to a purpose label whose two behavioural values are MIGRATED away, not merely tolerated.**
Why (expense module Phase 2): the single `type` list offered "fixed" and "variable" beside "marketing" and "payroll", so an expense could say what it was for OR how it behaved — never both. "Marketing and fixed" (an agency retainer) was unsayable, and nothing could be classified fixed and mean it, which is why break-even read Rs 0. Migration 0012 adds `cost_nature` (`fixed | variable | semi_variable`), backfills it from the old type using the same mapping `natureForStoredPurpose` implements and unit-tests, then rewrites the two behavioural types onto real purposes (`fixed`→operational, `variable`→custom). Rewriting rather than tolerating is safe because profit reads frozen cost snapshots on lines, never this catalog label — no historical money moves, only the label a P&L expense breakdown groups under. The write path now takes a narrower `expenseItemPurpose` enum so the conflation cannot return; the read enum keeps all eight values as cheap insurance. Named `cost_nature`, not the spec's `cost_behavior`, because `behavior` already exists on the same table meaning something else (`one_time | recurring | usage_based`) and the two sitting side by side would be a standing bug factory.

**2026-07-27 · Break-even moves variable PERIOD expenses into the margin instead of into the fixed base; the reconciliation contract is that true profit is zero at the target.**
Why: the textbook `fixed ÷ contribution margin` assumes every cost is either a direct cost of a sale or a fixed overhead. This ladder has a third place money sits — period expenses, below contribution profit, containing both kinds mixed (ad spend grows with sales, rent does not). Counting all of them as fixed overstates the target; counting only the fixed ones and stopping ignores that ads must be paid for too. So `r = (contribution − variable expenses) ÷ net revenue` and `break-even = fixed ÷ r`, which makes `true profit = rN − F` identical to the ladder's `C − (V + F)` and therefore exactly zero at the target. `lib/domain/breakeven.ts` is the only implementation; `breakEvenReconciles` states the contract in code, the server asserts the fixed+variable split equals `ladder.periodExpenses` and throws rather than shipping a break-even that disagrees with the P&L on the same screen. The server split also counts adjustment fee lines (a chargeback fee) that the P&L's own expense-type breakdown skips — so break-even reconciles to the ladder where that breakdown currently does not.

**2026-07-27 · Semi-variable is storable but counts as fixed for now; unclassified spend counts as variable and is shown.**
Why: splitting a semi-variable cost into its base and its usage part needs the allocation machinery scheduled for Phase 4/5. Until then it sits with fixed, which errs toward a HIGHER break-even target rather than a flattering one, and the UI says so in words ("Counted as staying the same until you can split it"). Unclassified spend — a label-only line, which zero-catalog fast entry makes a normal case, not an edge one — reads as variable: either choice raises the target, and variable avoids telling an owner that an ad-hoc purchase is a standing monthly commitment. The amount is returned as `unclassifiedExpensesCents` and surfaced on the page so the owner knows what would sharpen the number.

**2026-07-27 · Break-even is scoped to the SELECTED PERIOD, not "monthly"; a missing target is a reason, never a zero.**
Why: the page has always had a date-range filter while its break-even card said "monthly", so a 7-day range silently answered a monthly question. The endpoint now answers for whatever window is selected and the copy says "in this period". And because the failure this phase exists to kill was a confident Rs 0 on screen, the response carries a `reason` (`ok | no_fixed_costs | no_sales | no_margin`) that the UI turns into the right sentence — a period with no sales says so instead of claiming a Rs 0 target, and a business losing money on every sale is told to fix the margin, because no volume of sales would ever cover its fixed costs.

**2026-07-27 · Starter expense types are seeded at business creation and TOPPED UP when the owner changes business type; duplicate names became a plain-English error.**
Why: the seeded list is a convenience, never a permission — expense types stay user-created and unlimited (the 2026-07-27 gating decision stands). Seeding at creation alone would leave anyone who signed up on the default `ecommerce` and later switched to `service` stuck with a courier-shaped starter list forever, so a type change inserts the new type's starters with `onConflictDoNothing`: additive only, so nothing an owner renamed, re-natured or archived is touched. Every starter states its nature explicitly rather than leaning on the purpose default, because the defaults are a coin-flip on broad buckets — courier fees and rent are both "running the business" and only one grows with sales. Because every business now starts with a seeded list, typing an existing name became a likely mistake: `createExpenseItem` checks first and says "You already have an expense called X" instead of surfacing a unique-constraint error, and seeding/demo paths use `findOrCreateExpenseItem` so they adopt a starter rather than colliding with it.

**2026-07-27 · Every money event carries TWO dates: `occurred_at` (when it happened) and `paid_at` (when the cash moved, null = unpaid). Profit reads the first, cash reads the second.**
Why (expense module Phase 3): with one date, "did I make money in July" and "did I have money in July" were forced to give the same answer, and one of them was always wrong — a July bill paid in August could sit in only one month. `transactions.paid_at` (migration 0013) splits them, and `lib/domain/basis.ts` owns the rule both the server query and the UI copy read. `loadPeriodTransactions` takes a basis: accrual filters and files by `occurred_at`, cash filters and files by `paid_at` and drops anything unpaid outright (an unpaid row is ABSENT from cash, which is a different claim from being zero there). `GET /reports/pnl` gained `basis`, defaulting to accrual because profit is the question the ladder exists to answer. Verified on the dev business for 2026: accrual net revenue Rs 18,592 vs cash Rs 18,067, a gap of exactly Rs 525 — the two outstanding invoices, to the rupee.

**2026-07-27 · `pending` stops meaning "unpaid" and keeps only "not confirmed to have happened"; unpaid is a null `paid_at`.**
Why: `status` was carrying two unrelated meanings that need OPPOSITE treatment — an unpaid invoice is real and belongs in profit, while an unconfirmed recurring post has not been agreed to have happened and belongs nowhere. Sharing one value made it impossible to be correct about both. Migration 0013 converts pending rows the recurring engine did NOT create into `completed` with a null `paid_at`; unconfirmed recurring posts keep `pending` and stay out of both bases. This is the one place the change moves a figure, and moving it is the point: an unpaid July invoice IS July revenue. Consequences followed through: the header PATCH's settle toggle became `paidAt` (and refuses a pending row — "confirm this recurring entry before marking it paid"), unpaid-aging in Insights keys on `isUnpaid` so unconfirmed rows never appear on a chase-the-money list, confirming a recurring post now also stamps `paid_at`, and the legacy adapter's `paymentStatus` reads the paid date — it still read `status === "pending"`, which after the migration would have reported every outstanding invoice as settled and silently zeroed the legacy Cash Flow page's "Unpaid revenue".

**2026-07-27 · Reclaimable input tax is removed from the cost side; non-reclaimable input tax stays in it.**
Why: tax you can claim back was never really spent — the business is holding it for the tax authority — so counting it as a cost understates profit. `tax_paid_cents` + `tax_reclaimable` on the header (the counterpart to the existing `tax_collected_cents`, which is already excluded from revenue). The ladder subtracts the reclaimable amount from the SAME side the spend landed on, so the two cancel: a job's materials lift that job's contribution, a standalone bill reduces period expenses. It defaults to false because anyone not registered to reclaim really did spend that money. Deliberately header-level, mirroring `tax_collected_cents`, rather than per line — per-line tax needs the allocation machinery of a later phase, and a second money path would be worse than a coarse one.

**2026-07-27 · Foreign currency converts at a rate frozen on the transaction, applied ONCE at the read boundary.**
Why: `currency` and `fx_rate_to_base` existed on every transaction and were never set. They are now written and validated at create time and frozen there — the same rule cost snapshots follow, because tomorrow's rate must not move yesterday's profit. Conversion happens in exactly one place, `toBaseCurrency` inside `loadPeriodTransactions`, so every downstream read adds up in one currency without knowing anything about exchange rates; a conversion scattered across read paths would eventually be forgotten in one of them, and that path would report foreign money as if it were local. Cost snapshots convert too (they are stored in the transaction's currency — interpreting a frozen number is not mutating it), refunds inherit the ORIGINAL's frozen rate so they cancel the sale they reverse to the cent, and `toBaseCents` rounds the magnitude so a refund is the exact negation of its sale. The transactions LIST keeps its own loader and still shows amounts as entered.

**2026-07-27 · Phase 2's break-even reconciliation guard caught the tax change, and that is what it is for.**
Why (worth recording): adding reclaimable tax broke `computeBreakEvenReport` immediately — its fixed/variable split no longer equalled the ladder's period expenses, and the guard added in Phase 2 threw rather than serve a break-even that disagreed with the P&L on the same screen. The fix spreads the relief across the lines it came from with `allocateProportionally` (which sums to the total exactly, so no cent is lost or invented). The guard turned a silent cross-screen disagreement into a failing test on the first run; keep that pattern for any future rung.

**2026-07-28 · The expense module is PARKED at Phase 3; customer attribution takes the next block of work.**
Why (owner decision at the reassessment point the plan itself scheduled): Phases 0–3 solved the foundational problems — expenses carry a real fixed/variable flag, break-even computes from the ledger instead of reading zero, and profit and cash are finally separate questions measured by separate dates. What remains in Phases 4–10 is refinement (amortising a cost over months, splitting one bill across items) or ecommerce-only (per-order cost rules, RTO, ad sync), and both are worth less right now than knowing which customers are worth keeping. Nothing is abandoned or needs redesigning first: every remaining phase is additive against the core that now exists, which is exactly what "extend the ledger, never fork it" was for. `docs/expense-module-plan.md` marks each remaining phase *(parked)* with a banner saying they resume only on an explicit owner decision, so a future session cannot mistake "next in the list" for "next to build". Customer attribution is deliberately NOT scoped here — the owner is scoping it separately.

**2026-08-03 · A CSV import's `external_id` identifies a grid CELL, not a file row: person + target + date + work type + billable, never the hours or the description.**
Why (client-profitability Phase 7): hashing the row's content is the obvious design and it is wrong in the most common case. Fix one day in Toggl, re-export, and that row's content hash changes, so it lands beside the row it was meant to replace and the day counts twice — an "idempotent" import that silently doubles corrected days. Keyed on the cell, the same day always resolves to the same id, so `unique(business_id, source, external_id)` turns a re-import into an `onConflictDoUpdate` that RESTATES the day. Re-importing an unchanged file reports `unchanged`, writes nothing, and the ladder does not move. The id is built from RESOLVED ids rather than the names in the file, so renaming a client in Toggl does not orphan everything already imported for them. The trade this accepts: hours are not part of the identity, so an import can only ever say "this cell is now N hours" — which is exactly what a timesheet export means.

**2026-08-03 · Several timer rows on one day collapse into one time entry, with work type and billability kept in the key.**
Why: Toggl and Clockify export one row per started timer, but the grid — and `setTimesheetCell` — hold ONE cell per person/target/day. Writing five rows would have shown the grid one figure while the profitability engine counted another, which is the cross-screen disagreement every guard in this codebase exists to prevent. Two consequences followed and both are correctness fixes, not import conveniences: `getTimesheet` now SUMS the entries in a cell instead of letting the last row win (a latent bug manual entry could not trigger but import could), and `setTimesheetCell` replaces every entry in the cell rather than updating the first — typing a number means "this day was N hours", so leaving siblings behind would total more than the owner just typed. Work type stays part of the aggregation key so rework is never folded into the day's delivery at the import boundary; rework is the leading indicator the whole of Phase 6 rests on, and averaging it away on the way in would have destroyed the measure invisibly.

**2026-08-03 · An import with one unmatched name refuses the ENTIRE file, and hours typed by hand always win.**
Why: importing the rows that matched and mentioning the rest in small text is the failure this phase is designed against — a timesheet quietly missing one person's hours looks complete, and every client that person touched then looks cheaper than they are. Preview resolves exact name matches only and reports the rest with the closest existing records as suggestions; a "similar" match is never applied on its own, because four hours filed against the wrong client is invisible once it lands. Commit re-parses the FILE rather than trusting rows from the browser, since hours become money the moment they land. A cell that already holds hand-typed hours is reported as a conflict and left alone (never overwritten, never added to), and editing an imported cell strips its import id — so the owner's correction survives every later re-import instead of being restated back to what the file said. No CSV dependency was added: `lib/domain/csv.ts` is a hand-written RFC4180 reader and the domain still depends only on decimal.js.

**2026-08-03 · An estimate is spread across WORKING days and its parts sum to the typed total exactly; `source = 'estimate'` ranks below both typed hours and an import.**
Why (client-profitability Phase 8): the alternative to a rough figure is not a better one, it is NO figure — a business that will not fill a timesheet gets nothing at all from the profitability screen, and "we can't tell you" helps nobody. Three details keep it honest. Weekends are excluded, because spreading a month over all 30 days makes the estimate the one thing in the system claiming the team works Sundays, and both the short-day warning and the utilization figure read the calendar. The split is exact: 80 hours over 22 working days is 3.636…, so each day takes the total rounded down and the leftover hundredths go to the earliest days — "about 80 hours" that stored 79.98 would make every downstream figure disagree with what the owner typed for no reason they could ever see, and a total too small to give every day a hundredth lands on fewer days rather than writing zero-hour rows the CHECK constraint would refuse anyway. And `source` gained a third value rather than leaning on `is_estimated`, because the three RANK: typed hours outrank everything, a CSV import outranks an estimate (real hours replace the guess they stood in for, and the import reports how many it replaced), and an estimate is only ever replaced, never added to. A boolean cannot express an ordering.

**2026-08-03 · An estimate is refused on top of logged hours, and typing over an estimated cell makes it real.**
Why: guessing on top of facts doubles them and nothing on screen would say so, so `previewEstimate` returns a `blockedReason` naming the hours in the way and `setTargetEstimate` throws rather than adding. Re-estimating the same stretch deletes the previous estimate inside the same transaction before writing — a half-failed re-estimate that left both guesses side by side is exactly the doubling this exists to avoid. In the other direction, `setTimesheetCell` now clears `is_estimated` and the estimate's own note when a human types over an estimated cell and stamps it `manual`: somebody has said what the day actually was, so it must not keep carrying the "roughly" marker, and a later re-import must respect the correction. `clearTargetEstimate` filters on the estimate source rather than the date range alone, so clearing a guess never takes a logged day with it — verified live, where clearing a 60-hour estimate removed 57.14 hours and left the 6 that had been typed by hand.

**2026-08-03 · The page-level "these are estimates" warning is NOT scoped to one lens, unlike every total beside it.**
Why (a real bug caught during Phase 8 verification, not a design preference): `summariseTargets` deliberately totals ONE lens, because a sale to a client for a product appears under both and summing them doubles revenue. But `hasEstimates` was being taken from the same filtered set, so an estimate on a revenue item produced a row plainly marked "estimated" beneath a banner that said nothing — the page contradicting itself on the one point the whole feature rests on. The flag is now computed across both lenses via a second `allTargets` argument. A boolean is safe to take across lenses precisely because it is not money and cannot double; the totals still come from one lens only, and a test asserts the revenue figure is unchanged by the wider flag.

**2026-08-04 · A second reconciliation guard, on revenue: the client lens must equal the P&L's net revenue, or the request fails.**
Why (client-profitability Phase 9): the Phase 5 guard proved attributed labour never leaked out of the time entries. Nothing made the same promise about the money, so this page and the ladder could drift apart silently — and a change to discount allocation or shipping would have been the kind of thing nobody notices until an owner asks why two screens disagree. Every rupee of net revenue must now land on exactly one client row or in `unattributedRevenueCents`. The ladder it compares against is built from the SAME transactions the report already loaded, not a second query, so the two cannot answer for different data. Proven to fire rather than sit vacuously true: reintroducing the shipping bug produced `client-lens revenue 1000000 does not reconcile with the P&L's net revenue 1150000` on the first run. Verified live across eight period/basis combinations on the dev business, all reconciling to the rupee.

**2026-08-04 · Three pre-existing bugs the revenue guard found the day it was added, all in reads the owner was already looking at.**
Why (worth recording, because this is the second time a guard has paid for itself immediately): (1) **Refunds never came off a client's revenue.** The client lens skipped adjustment transactions outright, so a client's revenue was their GROSS while the P&L's was net — meaning the worst kind of client, the one who buys and returns, read as one of the best on the page built to spot exactly that. Refunds now reduce the client and the product, mirroring the ladder's own rule (a line reversing a sale line reduces revenue; a chargeback fee is a period expense and touches nobody's revenue). Because a refund line is label-only, the product is resolved back through `refunded_line_id` — one extra query, only when refunds exist. (2) **Shipping charged on a sale with no customer vanished from the client lens** while staying in the ladder. (3) **`GET /categories` had been returning 500 since Phase 1** for every business with seeded internal time buckets: `applies_to = 'time'` was written to the database but never added to the contract enum, so the endpoint failed its own response validation. A core endpoint broken by a feature that never touches it, and invisible because nothing tested a business that had the module switched on. A test now asserts the contract's applies-to list matches the database's, the same shape as the existing gated-feature-list test.

**2026-08-04 · The client nudges are gated inside `computeSignals`, and a broken profitability read costs its own nudges and nothing else.**
Why: `/reports/signals` is app-wide — the sidebar health chip and the Dashboard banner both read it — so putting `requireFeature` on the route would have 403'd all of that for every business not using this module. The gate belongs where the client-specific work begins, not at the door. And because the profitability report deliberately THROWS when its guards fail (right on a page whose whole job is that number, wrong on a business-wide feed), `clientProfitabilitySignals` catches, logs loudly, and returns an empty list — a test asserts every non-client signal is byte-identical when the module is broken or switched off. The nudges themselves inherit the module's rules: they never speak for an uncosted client (no loss, no "your best" — only "nobody has logged their hours"), they report the WORST case per kind rather than one per client so they cannot crowd the refund and margin warnings off the overview, and any sentence resting on estimated hours says so inside itself, because a signal is read alone with no table underneath it to check against.

**2026-08-04 · The client-profitability module is COMPLETE at Phase 9. These are the decisions that hold it together, and the ones a future session must not quietly undo.**
Why record this as one entry: the nine phase notes above were each written while the work was fresh, which makes them accurate and makes them scattered. What follows is the short list of load-bearing decisions — the ones where the obvious alternative is wrong in a way that is invisible afterwards.

**Attributed labour is a DISTRIBUTION of payroll, never a second cost.** Salaries already sit in the ledger as expenses. Time entries only decide which client or product carried each person's hours, so the profit ladder must not move by a single cent when hours are logged, imported, or estimated. Proven at every phase and again at Phase 9 across all eight money reports. If a future change makes the ladder move when hours are entered, the change is wrong, not the ladder.

**No hours means NO figure — never a zero and never a margin.** Revenue with nothing logged against it computes to full revenue at 100% margin, which is the most flattering possible lie about the client most likely to be losing money. Every labour-derived field is nullable and null means ABSENT: `isCosted` gates the row, `summariseTargets` totals costed targets only, and the Insights nudges refuse to speak for an uncosted client at all. A blank sends the owner looking; a confident wrong number stops them looking.

**Two figures, kept apart forever.** Contribution (revenue − labour − direct costs) is the primary one and carries no overhead. The fully-loaded figure is an ALLOCATION, labelled as one everywhere it appears, and enters no total that reaches the P&L. Fixed costs are never allocated per unit or per item — the invariant from CLAUDE.md, applied to people's time.

**Reconciliation guards THROW rather than serve a disagreeing number.** Two of them: attributed labour must equal the time-entries total (Phase 5), and client-lens revenue plus unattributed must equal the ladder's net revenue (Phase 9). Both have now caught real bugs within seconds of being written — the revenue guard found three on the day it landed, including refunds never coming off a client's revenue, which made the buy-and-return client read as one of the best on the page built to spot exactly that. A guard that has never fired is not evidence it is unnecessary.

**Every rate freezes at write time.** A time entry stores the rate that applied on ITS OWN day, exactly as a transaction line stores a cost snapshot. A raise in August must never restate what July's work cost — true for typed hours, imported hours, and estimated hours alike, including an estimate spanning a pay rise.

**Nothing is ever invented on the owner's behalf.** A short day warns and saves; it is never auto-filled to Admin. An import with one unmatched name refuses the whole file rather than importing the rest of it. An estimate is refused on top of hours somebody logged. In every case the alternative produces cost attribution that is fiction, and fiction is worse than a gap because it looks like data.

**The three write paths RANK: typed > imported > estimated.** Hours somebody typed are never overwritten or added to. A CSV import replaces an estimate (real hours beat a guess) but respects typed hours. An estimate is replaced, never stacked. Editing an imported or estimated cell by hand takes ownership of it permanently. That ordering is why `time_entries.source` carries three values instead of leaning on `is_estimated`.

**Server-side gating, scoped to this module only.** `requireFeature` is bound to the `/client-profitability` path prefix, not to the router — an early version bound it to the router, which runs on every request, and it 403'd `/api/data/reset` and broke the e2e. The Insights nudges are gated INSIDE `computeSignals` for the same reason: `/reports/signals` is app-wide and a 403 there would take out the sidebar health chip for every business not using this module.

**What is deliberately absent.** No CRM (no pipeline, stages, contacts, tasks). No time tracker (no timers, no mobile app) — a weekly grid, a CSV import, and an estimate. No export for this module yet, which is the one remaining gap, written up under "Known gaps" in `docs/client-profitability-spec.md` rather than left to be rediscovered.

**2026-08-04 · Cross-business isolation is now PROVEN rather than assumed, and the proof includes a control test — because a malformed call and a security boundary throw the same exception.**
Why: isolation in this module is structural — every service takes `businessId` as its first argument and the routes get it from `ensureBusiness(userId)`, never from anything the caller sends — so a request cannot name someone else's business. That made it tempting to call the property self-evident and move on. It is not: the caller still chooses the RESOURCE IDS, and "every query filters on businessId" is a claim about eleven services that nobody had checked. This is also the one class of bug in the module where being wrong is unrecoverable, since the thing leaking would be salaries. Four tests now cover it, all against two real businesses with full records: reads (every list and read excludes B by id AND by name, including the overhead default's headcount and every row on the profitability report), writes (eleven mutations aimed at B's records, after which B's people, rates, engagements and time entries are compared BYTE-FOR-BYTE against a snapshot — throwing and doing nothing are both passes, succeeding is not), name resolution (naming B's staff and clients in a CSV, which must come back unmatched with no suggestion pointing into B), and a control. The control is the part worth remembering: it runs the same eleven operations against the caller's OWN records and requires every one to succeed, because a call that throws on malformed arguments is indistinguishable from a call that throws on a business boundary, and a typo in the test would otherwise read as proof of security. Two of the eleven attempts are silent no-ops by design (the two deletes), and the control is what makes their silence mean scoping rather than a broken call. The suite was verified to bite by deleting the `business_id` condition from `clearTimesheetRow`'s delete — the most dangerous single line in the module — which failed the snapshot immediately and reported that attempt as a no-op that had nonetheless destroyed B's hours. One assertion in the first draft was wrong and the code was right: `listRateHistory` REFUSES a member outside the business rather than returning an empty list, which is the better behaviour, since an empty list is also what a real member with no rate history looks like.

**2026-08-04 · `engagement_type` and `billing_frequency` are REMOVED rather than made to work; each agreed figure now carries its own `total | monthly` period instead.**
Why: an audit of all 21 endpoints found both fields provably inert — validated, stored, round-tripped and printed as two columns on the Clients table, and read in no conditional, filter, sort, aggregation or arithmetic expression anywhere in the repo. Deleting them changed no number on any screen. The owner's call was to strip them rather than give them behaviour, on the reasoning that a field which looks meaningful and is not costs trust in every field beside it. What they COULD have told us — whether an agreed figure is monthly — is now asked outright, and asked TWICE: once for the hours and once for the money. One answer cannot govern both, because "forty hours a month against a fixed total fee" is a normal way to quote a retainer and forcing a single basis onto the pair would misprice the job by the length of the contract. Migration 0016 adds the columns defaulting to `total` (what every pre-existing row meant), 0017 drops the dead ones, and they are deliberately two migrations: the add is reversible and the drops are not, so mixing them would mean a revert of the drop could not happen without reverting the feature. Before dropping, 0016 uses what the dying column knew — rows with `engagement_type = 'retainer'` are backfilled to `monthly`, because an owner who picked "Ongoing retainer" was telling us the arrangement runs month to month. `billing_frequency` was NOT used as evidence despite `monthly` looking like it says the same thing: `monthly` is that column's default, so it sits on every row where nothing was ever chosen, and a default is evidence of nothing.

**2026-08-04 · Scope creep scales the COMPARISON to the window but never the PRICE, because the price is a ratio.**
Why: `agreedHourlyRateCents` is `agreed amount ÷ agreed hours`. When both figures share a basis, multiplying both by the window's months cancels exactly — so scaling them is not merely unnecessary, it is harmful: it forces a rounding on the cents and makes "you priced this at Rs 2,500 an hour" MOVE every time the date filter moves, which is the precise nonsense the scaling was meant to prevent. The price is therefore computed from the raw, unscaled pair, and only the hours are scaled for the over/under comparison. When the two figures use DIFFERENT bases the ratio is meaningless until both sit on one, and putting them there needs the contract's length; without `start_date` and `end_date` that length is unknowable, so the price returns a reason (`needs_dates`) rather than a number — inventing a length would misprice the job by however many months the guess was wrong. `monthsInWindow` prorates each calendar month by its own length so any whole month is exactly 1 and leap Februaries are free; an unbounded window returns null and a monthly agreement with no window is reported ABSENT, because defaulting to ×1 would compare a monthly figure against five years of hours and claim 6000% over. The multiplier reads the window through `windowDates`, the same hoisted derivation the time-entry query uses, so the numerator and denominator can never describe different stretches of time — a browser five hours ahead of UTC asking for "July" genuinely gets 1.03 months, and that is the honest answer for the window it actually sent, not a bug to round away.

**2026-08-04 · Engagement status decides what can be WRITTEN, never what can be read.**
Why: taking agreed hours from the ACTIVE engagement only had a consequence nobody intended — marking a client Finished erased their scope-creep record. The overrun really happened and their hours and revenue still counted in every other figure on the page, which is exactly what made it easy to miss, and it vanished at the moment the owner would sit down to review it. `selectEngagementForPeriod` now picks whichever agreement covers the window, live or not: candidates are those overlapping it (null dates mean open at that end, the common case since the dialog never sets dates — that single fact is what fixes the bug), ranked by overlap days, tie-broken live-first then later start, later creation, then id. The id step is not decoration: without a total order the answer depends on the order Postgres happened to return rows in, and the same report would give different numbers on different days. The related spec line promising "churned clients are excluded from current-period averages" was DELETED rather than implemented, because it is unimplementable: revenue lands on a client row by `transactions.person_id` with no reference to engagement status, so excluding churned clients would make client-lens revenue short by exactly their revenue and the Phase 9 guard would throw — the endpoint would 500 for any period containing a churned client's income. **2026-08-05 · Hours are guarded at the KEYSTROKE, not at the save, and every screen now sits under an error boundary.**
Why: typing a currency symbol into an hours box took the whole app to a blank white page. The server was never the problem — `isValidHours` has always refused it with a plain sentence — but the grid totals what is on screen AS YOU TYPE, and that arithmetic runs during RENDER, half a second before the debounced save fires. decimal.js throws on anything it cannot parse, React tears down the entire tree when a render throws, and there was no error boundary anywhere in the app, so one bad character in one cell produced no navigation, no explanation and nothing to click. Two fixes, because either alone leaves the failure mode intact. First, `hoursForTotal` in `lib/domain` makes the arithmetic untypeable-into: a value decimal.js cannot add counts as nothing until it becomes a number, and the accompanying test asserts the guarantee directly by feeding the crash inputs through it into `addHours`. Second, `isPartialHoursEntry` decides what to WARN about, and it is deliberately not `isValidHours`: that judges a finished value, while the grid needs a verdict on every keystroke, so "7" and "7." must both pass on the way to "7.25" or the warning becomes noise nobody reads. What it rejects is text no further keystroke can rescue — a symbol, a minus, a second point — and anything already past 24, since typing more only takes it further away. A bad cell keeps exactly what was typed (yanking a character back out from under the cursor is its own bug), marks itself, states why in words as well as colour, and is not saved; the save resumes the moment the value could be hours again. Verified by making a page throw, confirming the fallback with all 13 nav links alive, navigating away, and then removing the probe.

**2026-08-05 · One date rule for the whole app: nothing that already happened may be dated in the future, and a picked date is always a LOCAL calendar day. Recurring is the single, deliberate exception.**
Why: not one date box in the app was bounded, so a sale could be dated next year and then never be found, and a filter window could be set past today, hiding the rows the owner opened the page to see. The audit called this two bugs; it is one missing rule expressed in eleven places, now shared through `todayInputValue` / `isFutureInputDate` / `clampToToday` in `lib/finance`. The bound is applied twice on purpose: `max` on the input stops the picker, and the range setters clamp as well, because some browsers still let a date be typed. The stored global period is clamped on the way OUT of localStorage too — a custom window saved before this landed would otherwise survive the fix. The SECOND half was a genuine disagreement between two readings of the same string. `finance.ts` has always read a picked date as the seller's local calendar day, deliberately and with a comment saying so, because UTC day buckets hide after-midnight local entries from "Today". Quick Add and the transaction editor did not: they used `new Date("2026-08-05").toISOString()`, which is UTC midnight. In Pakistan that is 5am the same day and nothing breaks, which is exactly why it survived; west of UTC it is the previous evening, and every entry an owner dated "today" would land on yesterday in every filter, every P&L and every dashboard. Both now go through `dateInputToInstant`, which reads the local day — and, when the picked date IS today, keeps the current TIME rather than snapping to midnight, so "record it now" means now and two sales entered the same afternoon keep their order. A backdated day takes the start of that day, since there is no time worth inventing. The instant is stamped when Record is pressed rather than when the form was last edited, so a draft left open for ten minutes does not record a stale time. **2026-08-06 · Revenue items ARCHIVE rather than delete, archiving takes the variants with it, a variant tree can be changed after the item exists, and the first variant converts its parent.**

**2026-08-14 · "Offers below break-even once fixed costs are allocated" is refused, and recorded on the list as refused.**
Why: `CLAUDE.md` states that fixed costs are never allocated per unit or per item and that item-level screens stop at contribution profit. Allocating rent across offers requires choosing an allocation key; every key is arbitrary, and the resulting per-item "profit" moves when you sell more of something else. It looks like data and is not. Recorded in the catalogue with the reason so it is not proposed again, alongside what answers the same question honestly: offers below *contribution* break-even, the quadrant's Traps corner, and break-even at the business level on Money.

**2026-08-14 · Rules compare a business against its own normal, not against fixed thresholds. Build the baseline engine before the rule catalogue passes a dozen entries.**
Why: the existing seven rules in `computeSignals` fire on hardcoded thresholds, which will be wrong for half of all users — a 4% refund rate is a crisis for one business and normal for another. Comparing against the business's own history upgrades every rule at once and is what makes "anomaly of the week" possible at all. Retrofitting it after thirty rules exist means rewriting thirty conditions, so it goes early. Fixed thresholds survive only as floors.

**2026-08-14 (same day, REVERSES the ad-spend-table decision above) · There is no `ad_spend` table. Ad spend is an ordinary expense transaction on a source of kind `ad_platform`.**
Why: the earlier entry approved "a small table plus a logging screen", and building it turned out to break the thing the product rests on. `computeProfitLadder` reads `transactions` and `transaction_lines` and nothing else, so spend held in a table of its own would never have reached True profit — and for an ecommerce business advertising is usually the largest single cost, so the headline number would have been wrong by the whole ad budget while looking perfectly healthy. It also broke three invariants at once: the ledger is the single source of truth, engines write only through the same domain services, and a connector never invents a parallel money path. Everything the table was specified to hold already existed on the ledger: `source_id` is the platform, `occurred_at` is the day, `paid_at` makes prepaid credit and unpaid ad bills work, the line's `label` carries the campaign, `external_ref` plus the partial `unique(source_id, external_ref)` is the connector dedupe, and `origin` records where the row came from. So the feature shipped with **no migration at all** — a service, a contract, a route and a screen — and a future Meta/Google connector calls the same `logAdSpend` with `origin: "integration"`, which makes a replayed webhook a database-level no-op on day one. The integration test "ad spend reaches True profit" exists specifically to fail if anyone reintroduces a separate table.

**2026-08-14 · The "Advertising" expense item is created with `cost_nature: "variable"`, and that is load-bearing rather than cosmetic.**
Why: `computeBreakEven` folds variable period expenses INTO the contribution margin. Ads booked as fixed would push the break-even point outward and quietly corrupt every margin-adjusted figure built on top of it — including the break-even ROAS that the Marketing page is supposed to make its headline. Ad spend scales with selling, so it is variable, and the integration test pins the value so a future edit to the seeding path cannot flip it unnoticed.

**2026-08-14 · The legacy `ad_spend` Drizzle definition and the connector code that wrote to it were deleted rather than left in place.**
Why: `lib/db/src/legacy/adSpend.ts` named the same table the real feature now uses. It could only throw today, because migration 0001 dropped the table. But leaving a stale writer pointed at a name that now resolves to real rows is a hazard that costs nothing to remove and everything to discover later, so it went with the definition.

**2026-08-14 · Insight rules live in `lib/domain` as pure functions over a facts object the server assembles. A rule can never query.**
Why: the rules decide what the app SAYS about someone's money, so they are the last place drift or an invented number can be tolerated. Making them pure means the whole catalogue is unit-tested with hand-written fixtures and no database — twenty-nine tests that run in under half a second and can express "a shop whose refunds are normal must hear nothing" without seeding a shop. It also makes the boundary physical rather than a convention: a rule receives `InsightFacts` and returns a card, so it cannot reach past the read-models to compute money the ladder has not already computed. `services/insights.ts` fetches, `ruleCatalogue.ts` decides, and neither can do the other's job.

**2026-08-14 · Every insight card carries a money figure, enforced by the type and by `defineRule`, not by review.**
Why: "never render a card without a dollar figure — a rule that fires but can't be quantified is a log entry" was already written in INSIGHTS.md, and rules that cannot price themselves are exactly the ones a deadline produces. `Insight.impactCents` is required, `defineRule` drops any card whose impact is not finite, and a sweep test runs every rule against several business shapes asserting the same. The consequence worth stating: there is no "some expenses are unclassified" card, even though it is a useful thing to know, because the amount is real spending rather than money lost and booking it as either would corrupt the leak total the Summary toggle advertises. It belongs in a data-quality strip, which is different furniture.

**2026-08-14 · Rules compare a business to its own normal, and a period with no trading activity is NOT part of that normal.**
Why: the baseline engine (median + MAD, not mean + standard deviation, so one catastrophic month stays visible instead of raising the bar) was built so a 4% refund rate could be a crisis for a consultancy and a Tuesday for a clothing shop. The first live run exposed the subtler half: six history windows from before the business had recorded anything were being read as "a normal of zero", which produced "refunds are above your normal, normally Rs 0.00" and fired a "discounts are taking a big bite" card over Rs 80. A window with no activity is a period we know nothing about, not a period where nothing happened. Dead windows are now dropped before the normal is built, `baselinePeriods` counts trading periods rather than windows looked at, and the leak total on the seed fell from Rs 7,255 to Rs 525 — fewer cards, all of them true.

**2026-08-14 · A card may never contradict its own cause line.**
Why: the discount rule fired "Discounts are taking a big bite" above a cause line reading "0.0% of your sales", because unusual-for-you had been treated as sufficient on its own. A reader who catches the app contradicting itself in one field stops believing every field beside it — the same reasoning that deleted the invented Profit Drivers advice on 2026-08-11. Statistical unusualness is now necessary but not sufficient: the discount must also be a real share of the money before the card claims it is one.

**2026-08-14 · Urgency beats size WITHIN a subject, not only in the final sort.**
Why: found by the integration test, not by reading the code. "You are losing money" and "you sold more and kept less" are both about profit, and the second carries the larger figure — so the one-card-per-subject rule, which sorted by size alone, handed the subject to the milder card and demoted the urgent one into a "+1 more" line nobody reads. Dedupe now prefers the urgent card before it prefers the bigger one.

**2026-08-14 · `/reports/insights` is a new endpoint; `/reports/signals` stays as it is.**
Why: they answer different questions and have different consumers. Signals are ambient one-liners behind the sidebar health chip and the dashboard banner, and are deliberately currency-agnostic so they read correctly for any business. Cards put money inside their own sentences and therefore have to know the owner's symbol, which they read from `user_settings` and format with a trailing space to match the frontend's `formatCents` — "Rs3,000.00" beside "Rs 3,000.00" reads as two different applications. Replacing signals with cards would have taken out the sidebar chip for a gain nobody asked for.

**2026-08-14 · PQS exists. Three pillars — margin health, concentration, trend — each scored on a scale the drawer states in one sentence.**
Why: the score is a number we invented, so every design choice here answers "based on what?". Margin health is 0% kept scores 0 / 30% or more scores 100 — a stated absolute rather than an industry benchmark, because the app serves a freelancer at 60% and a shop at 12% and pretending to know the right margin for a business it has never seen is the invented-number failure in score form. Concentration is 20% or less from one name scores 100 / 60% or more scores 0. Trend has no absolute scale at all: it uses the baseline engine, so "normal" means this business's own recent trading periods, and at your own normal you score 50. Every pillar carries its raw inputs so an owner can re-derive it by hand from the drawer. Nothing benchmarks against other businesses — we lack the data and it is a trust minefield.

**2026-08-14 · A pillar with no data is ABSENT, never zero, and the remaining weights renormalise.**
Why: a business with no sales does not have "margin health: 0" — it has no margin health, and scoring it zero would drag the headline number down for a gap in the data rather than a fact about the business. Absent pillars drop out and the rest renormalise to 100, which is what makes "based on 2 of 4 measures" honest rather than a disclaimer on a fudged figure. A test asserts that dropping an average pillar RAISES the score, because that is the property a zero-scoring implementation would fail. The absent row is greyed rather than hidden so the gap is visible and explains the line above it.

**2026-08-14 · Concentration scores the WORSE of customer share and offer share, and the row routes to whichever drove it. This departs from the original brief.**
Why: the brief named customer concentration only and mapped the row to People. Taking the worse of the two makes the pillar mean something for both business types, which is the cross-vertical requirement in CLAUDE.md. Fixed routing would then have been wrong half the time, so the row routes to the page that owns whichever measure produced the score, and the drawer names it.

**2026-08-14 · Ad efficiency stays absent even though ad spend is now logged.**

Scoring ad EFFICIENCY means knowing which sales came from ads, and the attribution engine does not exist — `attributed_campaign_id` is still an inert column. A pillar scored from spend alone would call a business that spends heavily and grows fast "inefficient", which is a judgment we cannot support. **2026-08-14 · The waterfall reconciles or the endpoint throws. `waterfallReconciles` is an exported, tested property, not an internal assumption.**
Why: the whole value of this chart is that the bars add up to the number printed beside them. So the guard throws rather than serving a disagreeing chart, matching the stance the client-profitability reconciliation guards already take, and the property is exported so a test can assert it directly instead of inferring it from the code that produces it.

**2026-08-14 · A waterfall step may be a CREDIT — money coming back — and dropping negatives is what broke the sum.**
Why: refunds recover costs. When a sale is refunded the ladder takes the goods' cost back off the period's direct costs, so the named cost components legitimately sum to MORE than the net figure — on the seed, by Rs 1,027. The first implementation skipped any remainder that was not positive, on the assumption that a negative bar was nonsense, and a unit test written from the same assumption asserted the bar's ABSENCE without asserting reconciliation. The live guard caught it on real data within a minute of the endpoint existing. Steps now carry a `credit` kind, drawn green because money returning did not cost anybody anything, and the test that enshrined the bug was replaced with one that pins the credit and the reconciliation together.

**2026-08-14 · Named splits are always reconciled against their own totals, and the difference is shown rather than dropped.**
Why: the P&L can break direct costs down by frozen cost-component name, but an expense line booked straight onto a job has no component name to sit under, and refunds hand cost back. Either way the named parts do not equal the total. Showing only the named parts would quietly lose money off the chart; a remainder bar keeps it honest in both directions, labelled for what it actually is ("Other costs of sales" / "Costs recovered on refunds").

**2026-08-14 · The fourth Money tile is "Cash that moved", not "Cash on hand".**
Why: the page brief asked for cash on hand, and a balance needs an opening figure the app does not hold. Inventing one would put a wrong number on the single most checkable field a business owner has — they can look at their bank. What we do know exactly is the cash-basis ladder: what was actually paid in and out during the period. The tile is labelled for that, with a hint saying it is not a balance.

**2026-08-14 · A percentage change is suppressed once it passes 999%, and the prior figure is shown instead.**
Why: against a near-empty prior period the seed produced "+71318.8% vs last period" and "+79357.5%". Both are arithmetically correct and neither tells the reader anything — the field looks meaningful and is not, which is the failure DESIGN.md names and the dashboard rewrite already deleted once. Past the threshold the tile says "Was Rs 250.00 last period", which is the fact the reader actually wanted from the comparison.

**2026-08-14 · Every Insights page is in the nav, including the ones the five-page rebuild will fold in or retire. Owner's call.**

**2026-08-14 · The quadrant map's X axis is MONEY BROUGHT IN, not units sold. This departs from the brief.**
Why: the brief said "volume on X", the obvious reading of which is unit count, and it is wrong for any business with mixed price points. Caught on the seed the moment the endpoint existed: a web build sold twice at Rs 32,550 each was the single biggest earner in the company and landed in **Dead weight** — on the same screen as a podium calling it the best thing they sell. Two mugs and two web builds are not the same amount of business, and the quadrant's own names (Traps, Dead weight) describe CONTRIBUTION, not headcount. Units now size the dot instead, which is the honest home for them, and the axis reads "Brings in more →". An integration test asserts the top earner can never be filed as dead weight.

**2026-08-14 · An offer with nothing costed against it is left OFF the quadrant map, counted and named.**
Why: `missingCosts` originally fired only when NOTHING in the business was costed. The partial case is both more common and more damaging: an uncosted offer reads as a flawless 100% margin, which parks it in Winners on no evidence AND drags the median margin up so genuinely healthy offers fall below the line. On the seed, four uncosted subscription plans pushed the median to 92.6% and pulled a real 70%-margin service under it. The midpoints are now taken from costed offers only, the uncosted ones are excluded and listed by name, and the page asks for their costs — which is the highest-value onboarding prompt in the app anyway.

**2026-08-14 · "Earns you the most" must be an offer that actually earns. In a period where everything lost money, no flip is reported.**
Why: the revenue-vs-profit flip compared leaders without checking the profit leader was profitable, so a period where every offer lost money produced "A brings in the most money, but B earns you the most" — where B had merely lost least. The page now says "Nothing you sold made a profit this period", which is the true sentence.

**2026-08-14 · "Losing them would take you to a loss" is priced off the customer's CONTRIBUTION, not their revenue.**
Why: this is the highest-value warning the product can produce for a service business, so it has to be right rather than dramatic. When a customer leaves, what disappears is what they contributed — the rent, the payroll and the software keep costing exactly what they cost. Subtracting their revenue would have overstated the damage on every business with fixed costs, which is all of them. The page therefore says either "Losing them would take you to a loss" or the honest alternative "Without them you would have kept Rs 72,077.72", and both are computed from the same ladder the P&L reads.

**2026-08-14 · Revenue with no customer attached is its own named segment on the concentration bar, never folded into "everyone else".**
Why: walk-in and unattributed sales are real money that cannot concentrate on anybody. Pooling them with the small named customers would overstate how spread the customer base is — on the seed, 24% of revenue has no customer recorded, and hiding it inside "everyone else" would have made a genuinely concentrated business look diversified. It is drawn at lower opacity and labelled "no customer recorded", which is also a quiet prompt to start attributing sales.

**2026-08-14 · "Gone quiet" is judged against each customer's OWN purchase rhythm, not a fixed number of days.**
Why: the same reasoning as the baseline engine. A monthly retainer client unseen for 60 days is a crisis; a customer who buys every eight months is fine at 60 days. Each customer's usual gap is their first-to-last span divided by their purchases minus one, and they appear once they pass twice that. Somebody with fewer than two purchases has no rhythm to break and is counted separately rather than judged — a single purchase is an event, not a habit that stopped. The tile shows a COUNT and a value; the table shows NAMES. Most tools report churn as a percentage, and a percentage is not something anybody can act on.

**2026-08-14 · A repeat rate is withheld below 20 customers rather than shown with a caveat.**
Why: on twelve customers the rate moves violently on one person's behaviour and the reader has no way to know that. The tile shows "—" with "Needs 20 customers before this means anything — you have 12", which is more useful than a number that will be wrong next week. Same rule as the brief's "never render a cohort chart on twelve customers".

**2026-08-14 · `concentrationSentence` in `workInsights.ts` and the new customer one are deliberately separate functions.**
Why: they answer different questions for different modules — the existing one is about client concentration inside the client-profitability module and takes its own `Concentration` type; the new one is about customer revenue concentration on the Insights People page and needs the money formatter. The barrel export collided, and the fix was to name the new one `customerConcentrationSentence` rather than merge two things that only share a word.

**2026-08-14 · The Marketing page ships WITHOUT attributed ROAS, because attribution does not exist. Every figure is blended and labelled blended.**
Why: nothing links a sale to the advert that caused it — `transaction_lines.attributed_campaign_id` is still an inert column and no connector fills it. The brief's channel table (Channel · Spend · Revenue · ROAS · True ROAS · CAC · Profit after ad spend) therefore cannot be filled honestly per channel, and a per-channel ROAS number would be invented. The page has no field named `roas` or `trueRoas` at all, and an integration test asserts their absence — a field with that name reads as attributed, and the absence has to be structural rather than a comment. What is shown says "came alongside" rather than "returned", and `BLENDED_CAVEAT` travels with the payload so the page cannot forget to print it.

**2026-08-14 · Break-even ROAS from the owner's OWN margin is the page's hero, and it needs no attribution at all.**
Why: "3× ROAS is healthy" is the rule of thumb every ad tool repeats, and it is a guess about someone else's business. At a 20% margin you need 5× just to break even; at 80% you need 1.25×. This app has real margin from frozen cost snapshots, which is exactly what ad platforms lack, so the multiple is exact where their advice is generic. It is also useful BEFORE any money is spent, which is why the figure still renders for a business with zero ad spend.

**2026-08-14 · The one-sided test: ads can be PROVEN to have lost money, and never proven to have made it.**
Why: comparing ad spend against ALL the margin the business earned gives a claim that survives any future attribution. If the ads did not cover themselves even when credited with every last penny of margin the business made, then they certainly did not cover themselves. The converse does not follow — plenty of margin proves nothing, because most of it had nothing to do with the ads — so the copy falls back to the break-even fact rather than declaring victory. A test pins both directions.

**2026-08-14 · Cost per new customer is NULL with no ad spend, not Rs 0.00.**
Why: found on the live run. Zero spend over 31 new customers is arithmetically Rs 0.00 each, and as a headline tile it reads as a triumph when the truth is that the owner did not advertise. Same failure as the suppressed percentage deltas on the Money page: a field that looks meaningful and is not. New customers are counted from `people.first_transaction_at`, which needs no attribution — the tile says "if ads brought them all", because that is the assumption being made.

**2026-08-14 · Marketing stays in the nav even with no ad spend, overriding the brief's hide rule.**
Why: `INSIGHTS.md` says hide the page entirely when no ad spend is logged and no account is connected — a greyed tab is a nag, an absent tab is a product that fits your business. The owner's standing instruction from earlier today is that no page is hidden while the rebuild is in flight. The page handles the empty case properly on its own terms: it states there is nothing to judge, offers the logging screen, and still shows the break-even multiple, which is worth knowing before spending anything. Revisit the hide rule when the five-page IA is finalised.

**2026-08-14 · An insight card may carry money that is AT STAKE rather than gained or lost. `exposure` cards are excluded from the Leaks view and its total.**
Why: the payment-habit rule forced the question. The cash sitting in the gap between paying suppliers and being paid is real, checkable and worth acting on — but it has not gone anywhere. Counting it in "you're leaking Rs X a month" would inflate the most persuasive number in the product with money that is merely late, and a leak total nobody believes is worse than having no leak total. Exposure cards rank in the feed like any other; they are simply absent from the Leaks filter and `totalLeakCents`. The card also carries `impactSuffix: " tied up"`, because the figure renders red like any negative and a red figure otherwise reads as money gone.

**2026-08-14 · The payment-habit gap is measured, not estimated, and both sides must be real measurements.**
Why: ★ almost nothing else on the market can compute this, because almost nothing else stores both dates — every transaction here carries `occurred_at` and `paid_at`. Medians rather than means, so one customer who paid after 200 days does not become the business's terms. Both habits must clear five paid transactions before anything is claimed: two bills and three sales do not establish how a business pays. A gap the wrong way round is good news and this rule stays silent about it. The money figure is the daily selling rate times the gap — the working capital the gap ties up at any moment.

**2026-08-14 · The payment-habit card states that only PAID transactions could be timed.**
Why: the slowest payers are precisely the ones still missing a `paid_at`, so the customer figure is optimistic by construction. That is a real limitation of the measurement and it is printed inside the card's own Explain ("Measured on 6 paid sales and 6 paid bills") rather than left for someone to discover. The same reasoning as the ad page's blended caveat: silently omitting the basis of a number is what destroys trust in every number beside it.

**2026-08-14 · Price staleness is read off the LEDGER, not the catalogue, because the catalogue has no price history.**
Why: `revenue_items.unit_price_cents` is a single column — edit it and the old price is gone. But every `transaction_line` freezes the price it sold at AND the resolved cost snapshot beside it, forever. So the ledger is the price-and-cost history, and a better one than a catalogue audit trail would be: it records what customers actually PAID rather than what the price list said, and an integration test proves that editing a cost today cannot restate what the card says about last March. ★ This is the insight only this schema can produce, and the effective-dated cost components are what make it possible.

**2026-08-14 · The same item on two channels is TWO price histories. Merging them hides real drift.**
Why: found on live seed data, and it is the kind of bug that would never have surfaced in a fixture. A mug sells direct at Rs 25 and on Etsy at Rs 28, because `revenue_item_sources.price_override_cents` sets the price and source-scoped cost components add the platform's fee — both documented features. Interleaved chronologically, the price looks like it changes every few days, so the rule concluded the owner had already answered the cost rise and stayed silent. It had missed a genuine finding: the direct cost went Rs 8.00 → Rs 9.00 in June and the direct price never moved, across 38 units. Drift is now keyed by (item, channel), and the card names the channel only when the item genuinely sells in more than one place.

**2026-08-14 · A win never hides a warning about the same subject.**
Why: the second correction to the one-card-per-subject rule, found the same way as the first. "Ceramic mug earns you the most" (+Rs 2,400) swallowed "Ceramic mug costs more than it did" (−Rs 1,200) because the win carried the larger figure. Nobody can act on a compliment; they can act on "its cost rose and you never repriced". Dedupe now orders urgent, then bad news, then size — so within a subject a loss always outranks a gain.

**2026-08-14 · The drift look-back is 18 months, not the reporting period.**
Why: a stale price is by definition an old one. "The price has not moved in 14 months" cannot be said from thirty days of lines, so this rule gets its own window — the one place in the engine where a fact deliberately reaches far outside the period on screen. It costs one extra transaction load (~120ms on the seed) and the endpoint stays under 300ms.

**2026-08-14 · The demo dataset is a SECOND seed (`pnpm db:demo`), not a replacement for the fixture.**
Why: `seedCore.ts` is the correctness fixture — every figure hand-computed, asserted to the cent by `seed.integration.test.ts`, and deliberately small enough to verify by reading. Growing it into eighteen months of trading would have destroyed the one property that makes it useful. `demoSeedCore.ts` is the opposite by design: 814 transactions shaped like a real business, so the Insights pages can be judged on a trading history rather than four transactions. Both post exclusively through the domain services — a scenario that cannot be produced by the same calls the UI makes does not belong in either.

**2026-08-14 · The demo is a story, not noise: each month is shaped to make one thing findable.**
Why: random data produces a plausible-looking app in which nothing is ever true, and the rules either never fire or fire meaninglessly. The eighteen months run steady growth (which is what gives every baseline a normal to work from), then a bad kiln batch, a discount blitz, a clay-cost rise the price never answered, an ad splurge, and — in April — the classic trap: revenue up Rs 234,000 and profit down Rs 194,000 in the same month. Thirteen of the sixteen rules fire somewhere in the year, and each fires because the underlying fact is genuinely there.

**2026-08-14 · Nothing in the demo settles instantly, because instant settlement erased a real insight.**
Why: the first pass paid retail sales same-day, which is superficially realistic and made the median days-to-be-paid zero — so the payment-habit gap could never fire however slowly the invoiced work was paid. Card sales now clear in three days, the marketplace pays out fortnightly, workshops are invoiced at three weeks and branding at five. That is both more truthful and what makes "you pay out before you get paid" visible, at Rs 503,600 of working capital in April.

**2026-08-14 · Customers who go quiet are held out of the random buyer pool.**
Why: four regulars are given a fading purchase history so the gone-quiet list has names in it. The first run produced only one, because the ongoing monthly rhythm kept picking them at random and refreshing their last-purchase date — erasing the very thing the list exists to show. They are now excluded from the pool, and the demo shows four names quiet for 184–276 days against a 31-day rhythm.

**2026-08-14 · Demo money is in realistic rupees, not toy amounts.**
Why: the first pass priced a ceramic mug at Rs 25 and studio rent at Rs 650, which made every screen read like a spreadsheet exercise. Everything was scaled ×100 to figures a Pakistani studio would actually see — a Rs 2,500 mug, Rs 65,000 rent, a Rs 180,000 branding package — and volumes raised until the business was genuinely profitable rather than quietly losing Rs 8,643 a year.

**2026-08-15 · A spread cost defers ONLY under accrual; cash always shows the full outflow.**
Why: the first cut made `computeProfitLadder` skip a capitalised line unconditionally, which silenced the lumpy month — and also made a Rs 95,000 purchase vanish from the cash view entirely, so the app would have said no money left the bank in April. Accrual answers "which months does this cost belong to"; cash answers "when did the money leave". The two questions have different right answers here, so the basis is now an argument to the ladder (`defersToSlices`), defaulting to accrual. Hiding a real outflow is worse than the lumpy month the spread exists to fix.

**2026-08-15 · Spread slices are cascaded on void; refunds still block it.**
Why: slices are children of the purchase via `parent_transaction_id`, the same hook refunds use, so the existing guard would have refused to void a spread purchase with "void the refunds of this transaction first" — about a transaction that has no refunds. A refund is its own money event the owner must deal with deliberately; a slice is bookkeeping the purchase generated, and leaving the slices alive after voiding the purchase would keep charging for something that no longer happened. The two are told apart by `adjustment_type`.

**2026-08-15 · The capitalised rule lives in `expenseLineSpends`, not at each call site.**
Why: seven read paths total expenses independently of the ladder — category groups, expense-type groups, the break-even fixed/variable split, client cost-to-serve, payroll. Any one of them that forgot the rule would print a Rs 95,000 equipment row above a Rs 3,958 expense total. Putting the zeroing inside the shared per-line function means they inherit it; break-even's existing reconciliation guard is what would catch a path that still slipped.

**2026-08-15 · A cost with an order-level discount cannot be spread.**
Why: an order discount is shared across a whole transaction, so a spread line's real net cost would depend on its neighbours — and the slices would be built from the pre-discount figure while the ladder still took the discount off in the purchase month, inventing profit. Rather than guess a split, the ledger refuses and says to put the discount on the line. One less quiet way to be wrong.

**2026-08-15 · The demo's second kiln is now spread over 24 months, and the April alarm survived — correctly.**
Why: April was carrying both an ad splurge and a Rs 95,000 kiln, and "you sold more and kept less" was reading the kiln as a profit collapse. Spread, the kiln contributes Rs 3,958 to April instead of Rs 95,000, and the alarm's size falls from about Rs 193,592 to Rs 102,550 — it still fires, because the ad splurge really did erode that month's profit, and the very next card names it. The right outcome was never "the alarm disappears"; it was "the alarm stops blaming an investment for a collapse that did not happen".

**2026-08-15 · Spread slices are hidden from the ledger LIST and from refund history.**
Why: both were found by opening the drawer on a real spread purchase, not by a failing test. The drawer printed the twenty-four slices under "Refund history", telling the owner a purchase they never refunded had been refunded twenty-four times — slices hang off `parent_transaction_id` exactly as refunds do, and nothing was telling them apart. And the list showed the purchase plus a near-identical Rs 3,958.34 row every month, thirteen rows a year for one kiln. Slices stay in the ledger and in every number on every page; they are simply not money events, so they are not in the owner's record of money events. The purchase row carries the whole story — "charged across 24 months — about Rs 3,958.34 a month". Refunds remain visible in both places, because a refund IS a money event.

**2026-08-16 · A split bill is N lines, not a new allocations table.**
Why: the ledger already carries many lines per transaction, each line already has exactly one target, and all seven expense read paths already total per line through `expenseLineSpends`. An allocations table would have been a second money path that every one of those paths had to learn about separately — the exact mistake the old `ad_spend` table made, where True profit silently excluded the entire ad budget. As lines, a split needs no migration and nothing downstream knows a split happened, because there is nothing to know.

**2026-08-16 · `target_type` / `target_id` were dead columns until now.**
Why: they were added as the foundation for this phase, and `clientProfit` has been reading them the whole time — so "what did Acme cost to serve?" answered zero however many bills the owner recorded, and nothing said the number was structurally empty rather than genuinely zero. Phase 5 is what finally writes them. On the demo, three clients now carry Rs 15,000 / 9,000 / 6,000 of a Rs 30,000 monthly freelance bill.

**2026-08-16 · Split weights are relative, not percentages that must total 100.**
Why: insisting on exactly 100 means refusing "a third each", which is a real way to split a bill and not expressible in whole percentage points. Someone typing 33 three times has stated a ratio perfectly clearly, and rejecting it would be the app being pedantic about the owner's own arithmetic. The screen says what will happen instead — "Splits 33 / 33 / 33" — and `allocateProportionally` guarantees the parts add back to the bill to the cent either way.

**2026-08-16 · The query-time, revenue-proportional split is refused, permanently.**
Why: the original Phase 5 plan included "per-revenue splits resolve at query time and are never frozen" — spreading the rent across clients in proportion to what each earned. That is fixed-cost allocation, which CLAUDE.md forbids: fixed costs are never allocated per unit or per item, and item-level screens stop at contribution profit. It is also the same thing already refused for per-item fixed costs. A split is a statement of fact the owner makes about one bill; it is never a formula the app invents. `overheadPerTarget` remains the one place a derived share exists, and it is quarantined so it can never reach contribution.

**2026-08-16 · The demo's four service clients now hold live engagements.**
Why: only a client with an active engagement is targetable, so the demo offered products and internal buckets but no Clients group at all — the whole point of splitting a bill could not be shown. Northwind, Belmont, Vero and Harbor Café now have one, and a Rs 30,000 freelance design invoice is split 50/30/20 across the first three every month.

**2026-08-16 · The "is this zero real?" question is asked of the PERIOD, not of each client.**
Why: a client's direct cost of Rs 0 was indistinguishable from "nobody filled this in" — the failure the three data states exist to prevent. But the hours fix (null per client) is the wrong shape here. Hours are always consumed, so no hours logged can never mean zero hours. Direct costs are different: a client with no subcontractor and no bought-in software genuinely costs nothing beyond labour, and nulling per client would suppress a correct figure for the majority to hedge against a minority. So `directCostCents` stays a plain number, and the page asks once, of the period: is there any cost here that could have named a client and didn't? Fully attributed → the zeros are true and nothing is said. Partially → the amount is reported and the page states that contribution excludes it.

**2026-08-16 · Fixed costs are a SEPARATE bucket, not part of the untargeted pool.**
Why: measured on the demo before deciding. A single pool would have reported Rs 2.1M of Rs 2.4M — 89% of costs — as unassigned every month forever. A number that can never reach zero stops being read, and worse, it implies the owner ought to split rent across clients, which is the exact thing splitting permanently refuses to do. Three buckets instead: reached a target (Rs 240,000), could have and didn't (Rs 471,755), never split by design (Rs 1,663,625). The gate watches only the middle one, so clearing it is work with an end. Unclassified costs count as splittable, not overhead — "we don't know what this is" is the state most worth looking at, and filing unknowns under fixed would hide them behind the one bucket nobody expects to reach zero.

**2026-08-16 · The cost buckets are reconciled against the ladder, and writing that guard found a bug.**
Why: the page claims to account for every cost. `attributionReconciles` asserts targeted + splittable + never-split equals the P&L's period expenses to the cent, and `computeClientProfitability` throws rather than answer if it does not — the same pattern as the revenue and labour guards already there. It immediately caught a Rs 2,500 chargeback fee falling into no bucket at all: a real period expense that adjustments can never target, now filed under never-split rather than silently lost.

**2026-08-16 · The demo turns client profitability on explicitly.**
Why: the feature defaults on for `service` businesses only, and the demo studio is typed `ecommerce`, so the entire client view — including everything Phase 5 built — was invisible in the demo. The studio sells branding, studio hire and workshops, so the view genuinely belongs to it; the seed now sets the override rather than leaving a whole page dark.

**2026-08-16 · Known gap, deliberately left: a cost recorded INSIDE a sale never reaches that client's cost figure.**
Why: `directByTarget` skips it, and the ledger refuses to target a cost on a transaction carrying a sale, so it can never be pointed anywhere. It is filed under never-split, which is honest — it is not the owner's to fix. But it means a service business logging job costs against invoices would see those costs missing from cost-to-serve. Rs 0 on the demo today. Fixing it means deciding whether a job cost counts against the client the sale names, which is a design call of its own rather than something to ride along on this pass.

**2026-08-16 · The app ships BOTH themes, system-detected, with a Light/Auto/Dark control. DESIGN.md's "light mode only" is retired.**
Why: the owner asked for it, and the old rule was already half-dead — `enableSystem` had been on and doing nothing behind `forcedTheme="light"`, so a laptop set to dark still rendered light. Dark is authored, not inverted: every `--pl-*` token has a counterpart holding the SAME contrast contract (4.5:1 text, 3:1 fills) and the same money semantics. Two rules deliberately flip in dark — the recessed panel goes lighter than the card (darker would collide with the page and the well would vanish), and the brand fill goes bright with a near-black label (on a dark surface the fill has to be the light thing to read as a button). Verified: 0 contrast failures across all 24 routes in both themes, desktop and 375px.

**2026-08-16 · Dark mode is the one place the shell is allowed a line.**
Why: rule 1 says surfaces separate by value, not by line, and that holds in light. At the top of the dark ramp a card and the page are a few percent apart and the card dissolves. Rather than exempt dark from the rule, the line and the shadow are tokens (`--pl-surface-line`, `--pl-surface-shadow`) that resolve to nothing in light — so `.pl-surface` has one recipe, not two, and no component decides for itself.

**2026-08-16 · The theme class is applied by an inline script in index.html, before first paint.**
Why: React cannot do it. By the time the app mounts the browser has already painted, so every load flashed white for a dark-mode user. Storage key `profit-loop-theme`, shared with next-themes, wrapped in try/catch so blocked localStorage falls through to the machine preference instead of throwing.

**2026-08-16 · Only the hero figure counts up, and it refuses to animate in a hidden tab.**
Why: a count-up says "this figure is the answer"; put it on six numbers and it says nothing and delays the page becoming readable. The hidden-tab rule is not polish — a background tab gets no animation frames, so a count started there freezes partway and is still frozen when the owner switches back. A half-counted number IS a wrong number, and this product's whole promise is that its numbers are right. `AnimatedNumber` skips the animation when `visibilityState === "hidden"` and lands on the true value if the tab is hidden mid-count.

**2026-08-16 · Exactly one nav item can be current, resolved by longest-prefix match.**
Why: `pathMatches` is a prefix test, so on /settings/preferences it said yes to both "/settings" and "/settings/preferences" and lit up two rows. The moving rail needs a single answer (one marker cannot be in two places), and `resolveActiveHref` was the right answer for the plain highlight too. The main nav and the bottom nav keep separate rail ids, because when the sidebar is collapsed Settings genuinely appears in both lists.

**2026-08-17 · The dense-analytical pass was cherry-picked onto core-rewrite and merged with the dual-theme work; both directions survived.**
Why: the owner built the dense pass (bordered strips, 12/14/17/22/56 type scale, mono figures, directCosts rung, four-slice ring) on a separate worktree branch while this branch grew the dual theme. Cherry-picking preserved authorship and messages. Where the two collided the resolution was always MERGE, not pick: the hero wears the brand wash AND the dense border (both additive on Surface), the chart keeps the dark-aware grid token at the dense pass's 12px tick, the sidebar keeps the moving rail at the type scale's text-sm.

**2026-08-17 · A dense grid divides with `--pl-grid-line`, one step stronger than the row hairline in dark; a bordered card cancels dark's inset value-line.**
Why: a row separator should stay quiet, but a grid division is structure — at the top of the dark ramp the row hairline cannot carry it. And without the cancel, a bordered card in dark wore two edges a pixel apart (the border plus the value-lift inset every card gets there), which reads as "unfinished" without anyone being able to say why. `.pl-bordered` sets the token rather than overriding the shadow, so `.pl-surface` keeps one recipe.

**2026-08-17 · Stat rows mount ONE primitive (`StatStrip`), and tiles turn dense through context.**
Why: five pages had each built the same strip a little differently, which is how a design system dies. The strip is one bordered object with hairline divisions; a page swaps its grid wrapper and the tiles follow — skeletons and conditionals included — with no prop threading.

**2026-08-17 · The cash card is labelled "as you set it", and "money owed" ignores the period filter.**
Why: there is no bank connection, so the cash figure is the buffer the owner typed into Settings — a card implying a live balance would be the most expensive lie on the page. The one thing the app honestly adds is pace: months of runway when burning, months of cover when not. And owed money is a balance, not a flow — an invoice from March is still owed in August, so the unpaid card reads the whole ledger as of today whatever the period filter says.

**2026-08-17 · The currency setting is a LABEL, not a conversion. The browser-side exchange-rate multiply is removed.**
Why: two halves of the app disagreed — `useFormatters().money` multiplied by `PKR_RATES[currency]` (hardcoded, stamped "May 2025") while `formatCents`, which every contract-API page uses, applied no rate. Same figure, two answers. The conversion is the half that goes, for three reasons in order of weight: it is money math in the UI, which the architecture contract forbids outright; the server already owns currency properly (every transaction freezes its own fx rate and `toBaseCurrency` converts to the business's base currency before returning); and a hardcoded rate goes stale the day it ships, so restating real profit through it — with nothing on screen admitting it — is worse than a mislabelled symbol. An exported report is worse still: the file outlives the session and never records which rate it used. Nothing changed on screen at the time, because the default currency is PKR and its rate was 1. Real multi-currency display, if ever wanted, belongs on the server beside the rates that are actually maintained.

**2026-08-17 · Money is never encoded by colour alone. Ever.**
Why: measured with a CVD simulator, money green (#30a46c) and money red (#e5484d) separate by ΔE 4.9 under deuteranopia — below the floor of 6, against a target of 8 — and it cannot be fixed by re-stepping: darkening the green made it *worse*, at 2.0. Green-and-red is the worst pair in the space and it is also the pair this product's entire meaning rests on. So the convention stays and the rule changes: every money mark also carries a sign, an arrow, or above/below-baseline position. `moneyMark()` in `lib/chartTone.ts` hands back the colour and its second channel together so they cannot be taken from different places, and `DivergingBar` splits its axis rather than left-aligning both directions. Position is the strongest of the three because it also needs no reading. Verified on the P&L page by stripping the page to greyscale and confirming direction still reads.

**2026-08-17 · Categorical chart colours are their own five validated slots (`--pl-cat-1..5`); the tag hues may never be chart fills.**
Why: the tag `-solid` values were authored as a tint carrying dark text, and measured as chart fills they fail badly — amber lands at 1.58:1 on white, teal and pink collapse at ΔE 1.1 under deuteranopia. The new slots pass all six checks (lightness band, chroma floor, CVD separation, normal-vision separation, contrast) in BOTH themes and are declared literally rather than aliased, because slot 1 equals `--pl-blue` in light but `--pl-blue` is a different value in dark. `--chart-1..5` — which had zero consumers and pointed at money colours — now alias these, so identity has one name and money keeps its own. Assign in fixed order, never cycle; a sixth category folds into "Other".

**2026-08-17 · A chart may not render its own loading or empty state. `ChartFrame` owns both, and `loading` is a required prop.**
Why: two charts told owners "Record a sale and this will show how your income moves over time" on every page load, because an empty array during fetch and an empty array because the business is new looked identical to them. Making the frame *available* would not have fixed that; making the bug unwritable does. `loading` is required so forgetting it fails typecheck, `empty` is only evaluated once loading is false, no primitive accepts an `emptyMessage` (so there is no second place the string could come from), and each primitive console-errors in DEV if mounted outside a frame. On refetch the last good render holds at reduced opacity rather than flashing a skeleton.

**2026-08-17 · Chart primitives take plain chart-shaped input, never `EndpointResponse<typeof …>`.**
Why: `Waterfall`, `QuadrantMap` and `ConcentrationBar` each typed their props as one endpoint's response, which welded them to that endpoint and meant no second page could import them — which is exactly why five other pages hand-rolled their own bars instead. The page does the mapping; the primitive knows nothing about the API. That single rule is what makes the layer get used rather than bypassed.

**2026-08-17 · Insights: a shape that comes back from the server gets drawn, not spelled out.**
Why: the same pattern ran through nine pages. `unpaidAging.buckets` is a distribution rendered as three centred tiles — the one form that cannot show a spread, so a business owed a lot but all of it recent looked identical to one owed the same total all 31 days old. `marginErosion` was a slide rendered as three numbers. The Marketing ROAS trio was three multiples that live on one axis rendered as a definition list, so the only question that matters (above the line or below it?) needed mental arithmetic. `fees` was a bar that negated its own delta so growth would come out red — a sign flip carried purely for the colour's benefit, where `Dumbbell` with `down-is-good` states it honestly.

**2026-08-17 · DeltaBar is retired; movers draw on ONE diverging axis.**
Why: Command Center and Profit Insights split gained from lost into two columns. They shared a numeric scale but sat nowhere near each other, so "did the gains outweigh the losses" had to be answered from memory. A centre rule puts both directions on one axis where the eye does that comparison for free — and position carries the sign without leaning on colour, which is the DESIGN.md 3a rule doing real work rather than being quoted.

**2026-08-17 · Orange stopped encoding data, and the last hardcoded colours are gone.**
Why: `Profitability` drew utilisation, client concentration and work types all in the brand orange — one colour encoding three different dimensions on one page, against the rule that orange is the mark and never data. `CommandCenter` and `ProfitInsights` drew the true-profit series in a TAG hue, and in its text value where a stroke needs the `-solid` fill. The two heatmap whites now take `--pl-on-fill`, so they are theme-correct rather than accidentally-correct.

**2026-08-17 · `Meter` gained `inline` and `target`, both narrow and named.**
Why: the frame guard caught a Meter inside a budget table row — a fair complaint with the wrong verdict, since a bar in a row is an indicator whose container already handles loading. `inline` is a named exemption rather than a general `skipGuard`, because the moment the escape hatch is easier to reach for than the frame, the frame stops being a rule. `target` draws the threshold a value has to clear, which is what turned the ROAS list into an answer.

**2026-08-17 · `DataTable` gained `sections` — rows under a heading with an optional subtotal.**
Why: the catalogue and the ledger both group (by type/category) and show a running subtotal per group. Letting those two pages keep their own `<table>` to preserve that would have defeated the point of a shared component, so grouping moved into it. Bars scale across EVERY row rather than per section — otherwise a small group's biggest row would draw as long as the biggest row overall and the groups would stop being comparable.

**2026-08-17 · Three tables stay hand-rolled, deliberately.**
Why: `TargetTable` (Profitability) uses `colSpan` so an uncosted row shows ONE "No hours logged" marker across the money columns instead of four dashes — that is a correctness message (there is no number to show, because showing one would mean inventing it) and a column-per-cell API cannot express a row that spans. The cohort grid is a heatmap that happens to use `<table>`: dynamic column count, colour-binned cells — it is a chart. Timesheet, the budget editor and the CSV import previews are editable grids, and `DataTable` renders read-only rows. Converting any of the three would have cost something real to gain consistency for its own sake.

**2026-08-17 · Raw Tailwind palette classes are gone from status colours.**
Why: transaction status had `bg-orange-500/10 text-orange-600` — a fourth colour system alongside `--pl-*`, shadcn, and the tag tones, and orange encoding data besides. Status is a label, so it wears tag tones; a half-refund is a shade of refund and takes pink next to red rather than borrowing the brand mark.

**2026-08-18 · Read loaders are deduplicated per HTTP request via `AsyncLocalStorage`, GET only.**
Why: one Insights page load asked the database 105 questions and read 76,652 rows for a business holding ~12,000 — it loaded the SAME window eleven times, because `computePnl`, `computeLeaks`, `computeBreakEvenReport` and the rest each assemble their own facts without knowing who already loaded them. That independence is worth keeping (it is what makes them testable alone), so the deduplication went into `lib/requestCache.ts` rather than into every signature as a threaded argument. Within one request the ledger cannot change, so two identical loads must return identical rows — reuse is a pure optimisation. The cache holds the PROMISE, not the value, so six callers inside one `Promise.all` share one query instead of racing to fill it afterwards. Scoped to GET because a request that writes must never read its own pre-write snapshot; scripts and jobs run with no store at all. Measured after: 48 queries, 46,541 rows. Wall time on a local database is unchanged — the queries were always parallel — so this buys database load, connection-pool headroom and Neon cost, not a faster first paint.

**2026-08-18 · Refund→item resolution fetches only the referenced original lines, not the whole ledger.**
Why: `computeItemAggregates` and `computeLeaks` each loaded EVERY transaction line in the business on every call, to resolve refunds whose original sale sits outside the reported window. Correct, but it read the entire ledger to answer a question about a handful of refunds, ignored the date filter completely, and got slower every month no matter how short the period was — 12,000 rows per call at 6,000 transactions, four times per Insights load. The refund lines name the originals they unwind, so only those ids are fetched now, still scoped by `business_id`. `services.integration.test.ts` covers the case the old scan existed for (sale in May, refund in June) and was verified to fail without the fix.

**2026-08-18 · `invalidateMoney` covers every ledger-derived query key, and the client caches reads for 60s.**
Why: the two were one decision, because the second is only safe given the first. `invalidateMoney` — the function whose whole job is "money changed, refresh everything money" — listed eight keys and omitted the entire Insights area: `insights`, `pqs`, `waterfall`, `offers-report`, `people-report`, `marketing`, `leaks`, `drivers`, `momentum`, `retention`, `cohorts`, `signals`, `break-even`, `client-profitability`. So recording a sale left the score, the cards and every report showing the business as it was before it. That was already a live bug for the two hooks that cached; a default `staleTime` would have spread it everywhere. With the list complete, invalidation refetches regardless of age, so the 60s default only ever suppresses a re-read of data nothing has touched. The rule for the list: "would a newly recorded sale change what this screen says?" — over-invalidating costs one refetch, under-invalidating shows a figure that is quietly wrong. Definition-shaped keys (`categories`, `sources`, `settings`, `recurring`, …) stay out.

**2026-08-18 · Known-slow, not yet fixed: the 18-month price-drift scan dominates the Insights critical path.**
Why: recorded rather than fixed, because the fix is not free. `computeInsights` loads eighteen months of transactions and lines on every call so `detectPriceCostDrift` can say "the price has not moved in 14 months" — one card, and by far the largest single load left. A narrower query would have to restate `toBaseCurrency`'s fx conversion, and a second implementation of that is exactly how one read path starts reporting foreign money as local. The honest options are to cache the drift result (it moves on a scale of months) or to give it a purpose-built loader that shares the conversion. Neither was in scope for this pass.

**2026-08-22 · The transactions list returns its own date buckets; the graph above the ledger is drawn from them.**
Why: the page needed a small in/out graph that obeys the filters, and there were only three places the arithmetic could live. The browser is out — the UI never computes money, and it holds 200 rows at a time while the graph has to describe the whole period. A separate report endpoint is out — `/reports/pnl-series` knows nothing about the source, status or search the owner has set, so narrowing the table would leave the graph describing a different business. So `listTransactions` returns `buckets` beside the `groups` it already computed, over the same full filtered set, at no extra query: the rows, the subtotals and the bars come from one pass over one set of facts and cannot disagree. In and out stay apart rather than netted — a day that took Rs 200 and spent Rs 30 is not a day that made Rs 170, and the netted version hides the spending, which is the half more likely to surprise.

**2026-08-22 · Bucket boundaries moved to `services/buckets.ts`, and the ledger graph steps through weeks.**
Why: `analytics.ts` owned `bucketStartOf` / `nextBucketStart` / `bucketLabel` privately, and `read.ts` cannot import it (analytics imports read, so it would be a cycle). Copying the three functions is how the same sale ends up under two different month labels on two screens, so the rule moved below both. `chooseBucket` also gained a week step for spans of 32–92 days: the catalogue chart's day/month/year ladder draws a quarter as three columns, which is not a shape.

**2026-08-22 · The transaction detail is one component in two containers, and the pinned card is never empty.**
Why: the drawer's body was 250 lines welded inside a `Sheet`, so a card pinned beside the table would have been a second copy — and a second copy is how the phone quietly becomes a worse design. `TransactionDetail` now renders content and no container: a `Surface` on wide screens, the same `Sheet` below `lg`. The two are mutually exclusive through `useMediaQuery` rather than `lg:hidden`, because a hidden sheet still mounts its overlay over the whole page. Selection has its own rule (`resolveSelection`, tested): the card opens on the newest transaction so a third of the screen is never blank, keeps whatever was clicked while the list refreshes underneath it, and falls back to the newest row only when its subject genuinely leaves the list.

**2026-08-22 · Transactions showed two date filters; the older one is gone.**
Why: the page mounted `TopBar` — which wraps `PageHeader`, which owns the app-wide period filter — and then rendered `TodayFirstDateRangeFilter` again underneath it. Two controls for one range, on the page most likely to be filtered. The page now mounts `PageHeader` directly, which is what §16 asked new pages to do.

**2026-08-22 · Worth having and Budget / Break-even were the last two pages with a second date filter; both are now gone.**
Why: the same duplication Transactions had, and the check that mattered was whether the second control was a separate page-local range. It was not — both passed `useGlobalPeriod()` straight in as `TodayFirstDateRangeFilter`'s `value`, so the two controls wrote to one piece of state and the lower one only ever restated the header. Deleting it changes no number: `Profitability` still reads `period.range` and `BudgetBreakEven` still reads `dateRange.range`. Both keep `TopBar` rather than moving to `PageHeader` directly as Transactions did, because `TopBar` already renders `PageHeader` and it is what carries Quick Add on these two screens. The budget page lost one real thing with its filter — the title "Actual spend range", which said what the dates governed — so that sentence moved into the planner's own description. No page renders `TodayFirstDateRangeFilter` any more; the component and `useTodayFirstRange` survive only as the shape `GlobalPeriodProvider` fills.

**2026-08-23 · People answers "what is wrong with these records," not "which one is worth having" — and a check that never ran is reported as absent, never as zero.**
Why: Worth having already answers which client is worth keeping, and Insights already answers how concentrated the revenue is. Building either question a second time into People would hand the owner two answers that can disagree. People's job is the one nobody else does: which records are missing something, and what that quietly breaks elsewhere. A future request to add a lifetime-value ranking to this page is answered by pointing at Worth having, not by building a second ranking here.

The harder rule is what "nothing wrong" is allowed to mean. A gap the page never checked — because a module is switched off, or its data has not arrived yet — must be ABSENT from the result, not present and reading zero. Reporting zero is a claim that the check ran and came back clean; reporting nothing is the honest admission that no claim can be made yet. That is the same bug, in a different shape, as a chart rendering its own empty message while its data is still loading: both dress "I have not looked" as "I looked and found nothing," and an owner cannot tell the two apart from the screen.

Getting that right needed BOTH the feature flag and a null-data check, not either alone — the one review caught the hard way. `enabled: false` does not clear a TanStack query's already-cached data, so the flag alone leaves a stale tile rendering after the module is switched off, showing a pay-rate gap for a business that turned pay-rate tracking off minutes ago. The null check alone fails the other direction: a query still in flight has `data: undefined`, and treating undefined as "checked, nothing there" reports a business as clean before the answer has arrived. Neither gate substitutes for the other; the next gated feature needs both, every time.

**2026-08-27 · R5.1 is no longer one lump. It is a date split that is done, two pages that are done, and four remaining pieces that can each land on their own.**
Why: the plan said the leftovers were one entangled ball centred on `lib/finance.ts` — do them together or not at all — and that rule was holding back work it never applied to. The file was two files sharing a name: a date half and a money half. Eleven of its twenty-seven importers wanted only the dates. They were waiting on a rewrite of money maths they never touched. Splitting the dates out took the importer count from 27 to 16 without changing a single number on screen, and moving two pages onto the server ladder took it to 14. The file list in the plan was stale on top of that: four of the files it told a future session to rewrite had already been deleted by earlier work, and two more had quietly stopped using `finance.ts` at all. The consequence of getting this wrong was not wasted effort, it was paralysis — a job costed as one impossible session instead of six achievable ones, so it kept not being scheduled. The lesson generalises: a plan that names files is a claim about the tree on the day it was written, and it gets re-checked against the tree before anyone costs it again.

**Budget cannot be moved onto server figures yet, and the reason is that its "actual spend" figure is a word search rather than a link — on every row, not just the unusual ones.**
Why: the page works out what was actually spent by searching expense text for words it hopes will match, and the only thing that changes from row to row is where the words come from. The six rows the page ships with use a hardcoded list each — the salary row adds up any expense whose name, category or note contains "salary", "staff", "payroll" or "wage"; the software row looks for "software", "tool", "subscription" or "saas"; rent looks for "rent" or "warehouse". A row the owner adds by hand has no list, so the page takes the row's own name, deletes the word "budget" from it, and searches for whatever is left. Ad spend is the single exception: it is a real total of real ad costs. Miscellaneous is not a total at all, it is what is left over after subtracting the others. So the software row misses the subscription recorded under its brand name, and picks up an unrelated expense that happens to have the word "tool" in a note. That is not a wrong total, it is a total that cannot be right or wrong, because nothing connects a budget line to the spending it is supposed to govern. Building a server endpoint that reproduces it would be the worst outcome available: it would give the guess the same authority as the profit ladder, and hide it behind an API where nobody can see it being made. Budget waits for a real link between a budget row and its expenses. Break-even on the same page already comes from the server and is unaffected.

**Financial Statements stays as a second profit-and-loss page, and the divergence is accepted rather than fixed.**
Why: the owner chose to keep both for now, and the point of writing it down is so the next session does not "discover" it as a bug and either delete a page the owner wanted or spend a day reconciling two pages on purpose. Being honest about what accepting it costs, because it is bigger than it looks: that page still works its own figures out in the browser, it uses the wording the ladder retired, and — the part worth stating plainly — it reads its sales and costs from the same local store the downloadable reports do, which only ever holds one page of 200 transactions. It opens on All Time, and it decides what "all time" means from the earliest and latest dates among those same 200 rows. That is the identical set-up that made Reports Overview briefly show Rs 4,014,600 where the real figure was Rs 16,293,400 — figures reproduced by re-running the deleted code path rather than sampled off the screen, so treat the scale as firm and the exact digits as an illustration (`docs/superpowers/reports/2026-08-26-r51ab-number-changes.md`, "How firm these before-figures are"). So this is not the roughly Rs 4,000-a-month disagreement the Forecasts page had; on the view it opens on, this page is very likely showing about a quarter of the business, and unlike the flash it never corrects itself. Known, accepted, and not an oversight — but accepted at that size, and live rather than dormant.

**Forecasts works out its month-end estimate in the browser, and that does not breach "the UI never computes money".**
Why: the invariant exists to stop the browser publishing a figure that contradicts the books. It is aimed at a real failure that has happened here more than once — a page adding up its own version of profit and putting it beside the ledger's, with nothing on screen saying which is which. A month-end estimate has no book to contradict. Nothing in the ledger says what August will finish at, because August has not finished. What the invariant does demand is that the figures the estimate starts from are the ledger's, and they now are: revenue, costs and true profit all come from the server, and the multiply is rounded straight back to whole paisa so no fractional money ever reaches the screen. The alternative was worse in a way that is easy to miss — putting the projection on the server would dress a guess about an unfinished month in exactly the same authority as a settled fact, and the owner would have no way to tell them apart.

**A figure that has settled but does not exist is shown as an em dash, and a profit margin does not exist unless net revenue is above zero.**
Why: there were three ways to fill a slot with no figure in it and two of them are lies. A loading placeholder that never resolves says "a number is coming" — which is false the moment a request has failed. A zero says "the number is zero", which is a claim about the business. The dash says "there is no figure here", which is the only one of the three that is true. The margin is the case that made it concrete: for a day with no sales, the page used to print `0.0%`, and an owner reads that as "you made nothing on what you sold" rather than "you sold nothing". A margin on zero revenue is undefined, not zero. The rule extends to the awkward end too: in a period where refunds exceed sales, net revenue is negative and a percentage is arithmetically available but means nothing, so that period also shows a dash. A reader may expect a number there. There is no number there, and inventing one is how the page loses the right to be believed anywhere else. What this entry does NOT settle, and must not be cited as settling: there was a fourth option it never named, an error state. A request that *failed* is a third case alongside "still loading" and "settled with nothing in it", and it is still unhandled on both pages — a failed `/reports/pnl` currently renders the same em dash as an empty period, which is not a lie but does understate it, because nothing on screen tells the owner the server did not answer. Deliberately deferred, not closed: it needs its own affordance, and until it has one these pages cannot distinguish "your business recorded nothing" from "we could not reach the books".

**Four tile labels were renamed onto the ladder's fixed wording, and that was mandatory rather than cosmetic.**
Why: the architecture fixes one vocabulary — Gross revenue, then Net revenue, then Contribution profit, then True profit — and requires it verbatim in the UI, precisely because "profit" and "revenue" each have several possible meanings in this app and a tile cannot say which one it is showing. Each of these tiles now renders one named rung of that ladder and nothing else, so the label has to be the rung's name. "Revenue" became **Net revenue** and the retired string "Net Profit" became **True profit** on Reports Overview; "Expected profit" became **Expected true profit** and "Expected revenue" became **Expected net revenue** on Forecasts. That fourth one is the one worth dwelling on, because it was nearly missed: the argument for qualifying "profit" is that the word has four meanings here, and it applies to "revenue" with no modification at all, since the ladder splits that into gross and net. Renaming one card on a row and leaving its neighbour vague would have shipped a page that looks careful and is only half converted, which is worse than one that is uniformly loose — a reader trusts the precise label and then assumes the imprecise one beside it was equally considered. Where a tile renders a rung verbatim it now takes its text from `LADDER_LABELS` rather than spelling it out, so a future rewording of a rung moves the screen with it instead of leaving it behind. No figure changed because of a rename, and the cost of getting it wrong is not aesthetic: the same page also offers a downloadable file, and a screen and a file that use different words for the same rung is how two people end up arguing about which number is real.

**2026-08-27 · The Reports download reads server totals and never raw rows. The payload carries no transactions at all.**
Why: the old export was handed at most 200 transactions by the browser store and asked to add them up, so on All Time it described roughly a quarter of the business while the screen beside it described all of it. Moving the sums to the server would have fixed today's numbers and left the trap open, because the next person to add a column to that file would reach for the rows that were sitting right there. So the payload the export receives has no rows in it. There is nothing to sum. A figure can only reach the file by being asked for from the server, which means a future edit that wants a new figure has to go and get a real one. Measured on the live ledger after the change: the workbook's net revenue Rs 16,113,400.00 and true profit Rs 2,224,146.03 match the screen to the paisa, over 858 transactions rather than 200.

**2026-08-27 · The Offers sheet stops at contribution profit, and its revenue is not expected to equal the ladder's net revenue.**
Why: fixed costs cannot be divided across offers by any method that is not invented. Rent does not belong to the ceramic mug in some ratio the software worked out on its own, and an accountant asked to justify that ratio would rightly refuse. So true profit appears once in the file, on the Summary sheet, where the costs it subtracts are real; the per-offer sheet stops at the last rung that is honestly per-offer. The consequence to state plainly, because it looks like a bug and is not: the Offers sheet's revenue column does not add up to the ladder's net revenue. Measured on the live ledger, it came to Rs 16,352,200.00 against a net revenue of Rs 16,113,400.00 — Rs 238,800.00 more, which is exactly the sheet's own Refunded column and exactly the ladder's Refunds rung, because per-offer revenue is counted before refunds and the refunds are shown beside it. The same shape appears on the Costs sheet, where the Spent column came to Rs 5,378,997.97 against period expenses of Rs 5,381,497.97 — Rs 2,500.00 short, which is one chargeback fee that is a real cost of the period but belongs to no catalogue item, so no per-item row can hold it. Forcing either column to agree would mean either hiding real money or inventing a row to put it in. Both figures are in the **workbook**, so a reader who wants the bridge can do it from the workbook itself — Gross revenue, Discounts and Refunds are rungs on its Summary sheet. That is not true of the PDF, which renders four KPI cards and no ladder, so none of those three figures appears in it at all; a PDF reader who spots the gap has to open the Excel file to close it.

**2026-08-27 · Both download buttons are disabled until every figure has arrived, and the reason is visible text rather than a tooltip.**
Why: the screen's rule is never to show a figure it does not have, and that rule is stricter for a file than for a page. A page corrects itself a second later and the reader sees it happen. A file leaves the building, carries no record of how it was made, and is opened a year later by someone who was not in the room — so a workbook headed with a placeholder business name, or missing a sheet because one of four requests had not landed, is a permanently wrong document with nothing on it to say so. All four requests are therefore one gate: no payload, no file. The second half of this is not a style choice. The shared button carries `disabled:pointer-events-none` (`button.tsx:15`), which means a disabled button is skipped by hit-testing entirely and the browser resolves the hover to its parent — so a `title` tooltip on it sits in the DOM, passes any test that inspects attributes, and shows the reader absolutely nothing. Four greyed-out buttons and no explanation reads as broken software. The reason is rendered as text for that reason, and because text survives touch, where hover does not exist at all.

**2026-08-28 · A column in the exported report declares what it HOLDS, and that alone decides how precisely it may be printed.**
Why: the PDF used to work out precision by looking at each column's heading — if the words contained "(%)" it kept one decimal, and otherwise it rounded to whole units. That rule was written while thinking about money, and money is the only thing it is right for. It was silently applied to the Offers sheet's quantity column, which is not money and is not whole: quantities are decimals in this app by architecture, so a freelancer logging 7.5 hours got 7.5 in the workbook and "8" in the PDF, and any quantity under a half printed "0" next to a real revenue figure. Nobody saw it because the development data only ever has whole quantities. Each column now carries a kind — money, percentage, quantity, count or text — written on the same line as its heading in `reportSheets.ts`, and both the workbook and the PDF read it: money whole, percentages one place, quantities up to two, counts whole. The decision moved into the module that has tests, and a column added later arrives already described instead of being guessed at. The general rule worth keeping: a document must not infer what a number MEANS from how it was labelled.

**2026-08-28 · The exported file uses the app's own words for a cost, taken from `lib/domain` — it does not invent accountancy terms of its own.**
Why: the Costs sheet was printing database values. Its Type column said `cogs` and its Behaviour column said `semi_variable`, while the Summary sheet a few rows above rendered the very same stored value as "Cogs" — one enum, two spellings, in one workbook, and "COGS" is a word this project bans everywhere else. The starter catalogue gives `cogs` to four costs of every new business, so this was not an edge case; it was the default. Both sheets and the PDF now label a cost through one map, and that map is `EXPENSE_PURPOSE_LABELS` / `COST_NATURE_LABELS` in `lib/domain` — the same words the Expenses page shows. Writing a second, more accountant-sounding vocabulary just for the export was the obvious alternative and was rejected: it would have made the file disagree with the screen, which is the same defect one level up, and an owner asked by their accountant "what is this row?" must be able to point at their own software and see the identical phrase. A `cogs` cost reads **Cost of goods**; `semi_variable` reads **A bit of both**. The tests now assert that no cell in any sheet contains an underscore, and the banned-word check is case-insensitive, because the exact-case version had been passing while "Cogs" shipped.
**2026-08-28 · The QueryClient is left exactly as it was: `networkMode` stays at the default. The reported "money screens can never show an error" was measured and is not true.**
Why: the claim was that React Query's default `networkMode: "online"` pauses any failed request, so a failed money query can never surface. Measured against the real library at the app's real settings (`retry: 1`), in `artifacts/profit-tracker/src/api/queryFailureModes.test.ts`: on a visible, online tab an HTTP 500, a refused connection and a timeout are indistinguishable to the retryer and all three reach `status: "error"` after two attempts. The reviewer who disputed the diagnosis was right. What was actually observed is a second, unrelated pause path: `createRetryer`'s `canContinue()` is `focusManager.isFocused() && (networkMode === "always" || onlineManager.isOnline()) && canRun()`, and `focusManager.isFocused()` is `document.visibilityState !== "hidden"` — so a HIDDEN document pauses the retry, which is the permanent state of an agent-driven browser tab. The two pauses are told apart by the attempt count: offline pauses before the first attempt (`canStart`), a hidden tab pauses after it (`canContinue`). Setting `networkMode: "always"` was therefore the wrong fix twice over — it does not reach the focus term at all (measured: still paused), and the offline pause it does fix is worth keeping, because it sends no requests into a dead network and resumes by itself on reconnect. The hidden-tab pause needs no fix either: looking at the page is what un-pauses it (`Query.onFocus` calls `retryer.continue()` regardless of `refetchOnWindowFocus`), so no owner can ever be sitting in front of one.

**2026-08-28 · A figure has four states, not two, and which one it is now decided in one module (`lib/figureState.ts`) rather than from `isLoading` at each call site.**
Why: this closes the error state DECISIONS.md left open on 2026-08-27 as "deliberately deferred, not closed". The trap is that `isLoading` is `isPending && isFetching`, so a request that FAILED and a request that STOPPED both report `isLoading: false` — and every page that branches on it falls straight through to its "we have nothing" rendering. Three screens did, and they degraded by increasing severity: Forecasts and Reports printed the same em dash an empty period gets, which understates it; the Reports download went further and said "Waiting for this period's figures" about a request that was not waiting for anything; and People printed "No customers yet." on a list that never arrived, which is not an understatement but a false statement about the business, of exactly the kind the "no page may show a figure it does not have" invariant exists to stop. So `figureState` returns `loading | settled | offline | failed` from the three flags, `settled` keeps the em dash (an empty period really did answer, and the answer was nothing), and the other two get words: "Couldn't load" / "The server didn't answer", "Offline" / "will appear when you're back online". A figure already in hand outranks all of them, so a failed refetch never blanks out a good number — the rule ChartFrame already follows. Rendered in amber, never red: colour in this app means money (DESIGN.md §2) and a request that did not land is not money lost; the People gap strip had already reasoned its way to amber for the same class of signal. Verified in the running app against a live ledger — an injected 500, an injected refused connection, and a real `offline` event each produced their own wording on all three pages, and People's "Try again" recovered the list.

**2026-08-28 · The figure states are applied across the app, and the audit found that the worst cases were not em dashes but sentences, zeros and all-clears.**
Why: `figureState` closed the defect on three screens; twenty-three more still branched on `isLoading` alone. Reading each one for what it renders when a request fails or pauses sorted them into three kinds, and the ranking was not the expected one. The mildest are the em dashes, which understate. Above them sit the screens that claim to still be working — "Working out your score…", "Following the money…", a skeleton that pulses for ever — which are the Reports download's "Waiting for this period's figures" in another costume: a wait that is not a wait, asking the reader to keep waiting for an arrival that is not coming. The worst are the ones that answer a question they never got an answer to, and there were far more of them than the em dashes: Dashboard's owed card printing "Rs 0" under "Every sale is paid for."; "Nothing is flagged right now."; Transactions' "0 transactions"; the catalogue totals printing Rs 0; "No recurring schedules yet" on a business whose rent posts automatically; "Nothing logged this week"; Ad spend's "Until it's here, your profit looks better than it is"; Budget's "Under budget · You are under your planned expenses"; Clients' four simultaneous all-clears including "None — every subscription is current."; and the sharpest of all, the person sheet answering "Not found" for a customer the owner had just clicked. Every one was reached from a `?? []` or a `data ? … : 0` standing in for a request that never landed. Two of the fixes are structural rather than per-page, because the same sentence was being produced in one place for many screens: `ChartFrame.loading: boolean` became `state: FigureState` — a boolean was literally one state short, and `empty` is now read only when the state is `settled`, so an `emptyMessage` like "No revenue recorded in this period." is unreachable from a failed request by construction, with the required prop keeping the original typecheck guarantee. And `InsightFeed` took the same treatment, because "Nothing needs your attention this period." over a leaks tab reading "Leaks · none" is the most reassuring thing the product says, and it was being said about a business the app had not managed to look at. The legacy `useStore` gained `dataState` for the same reason: its `isLoading` was an OR of four `isLoading` flags, so three Dashboard blocks and the whole Budget page were doing the arithmetic of nothing and presenting it as fact. Integrations is in the list despite holding no money: an empty list made every card draw itself as NOT CONNECTED with a Connect button on an account that may already be syncing, which is a false claim with a real consequence behind it. `FigureSlot` was extracted after the third identical ternary, and holds the one rule easiest to lose in a hurry — words that stand in for a figure never wear `tabular-nums`, because anything numeric-looking in a money slot gets read as an amount.

**2026-08-29 · Cash Flow finishes the figure-state pass, and a half-converted page turned out to be worse than an unconverted one.**
Why: Cash Flow was not on the audit list of twenty-three. It was touched anyway, because `ChartFrame.loading: boolean` became `state: FigureState` and its three frames had to be given `dataState` — and that left the page arguing with itself. The frames correctly said "The server didn't answer." while the four tiles directly beneath them printed "Still owed to you Rs 0 · Every sale is paid for" and "Bills not paid Rs 0 · Nothing outstanding", and the block below THOSE showed a green "Low" tag over "Your tracked cash position looks stable for this period." A reader taking the page at face value would have concluded the business was in good shape from a screen that had just admitted it could not reach the books. Three things were fixed and each names a different way the shape hides. **The tiles** are ordinary `FigureSlot` work, except that their hints split in two: a hint that MEASURES ("Every sale is paid for") is suppressed until the store settles, and a hint that DEFINES its label ("Owner draw — not a business cost") stays, because it is true whatever loaded and the amber slot above it already says the figure is missing. **The hero figure** looked already-safe and was not: it was gated on `!empty`, which holds only while ALL FOUR store queries fail together — one failing (transactions land, expense items do not) leaves `empty` false and prints a confident signed total built from half the money. Verified in the running app on all four states.

**2026-09-03 · A workspace is a BUSINESS; a construction site or production run is a PROJECT. One user may own many businesses.**
Why: the owner asked for two containers in the same week and both wanted the word "project" — a separate set of books to switch between, and the thing a builder's costs belong to. Letting both have it would have made every screen ambiguous at exactly the point where money is attributed. "Business" is what the `businesses` table has always been called and what an owner says out loud ("my other business"), and "project" is the trade's own word for a site, a contract or a production run, so the pair reads naturally in both directions: Ahmad Builders → Gulberg Villa, Phase 2. Manufacturing sees "Production run" through a per-type label map rather than a second concept. The alternative considered and rejected was "Workspace", which is unambiguous and is also software jargon in a product whose whole promise is plain English to people who do not read software.

**2026-09-03 · Every request names its business in a header, and every request verifies the caller owns it. Not-yours and does-not-exist answer identically, with 404.**
Why: one business per user made scoping implicit and therefore safe by accident — the session named the user, the unique index named the business, and there was nothing a caller could get wrong. Dropping that index (migration 0021) turns the business id into client-supplied input that reaches money, which is a door. `middlewares/requireBusiness.ts` is that door and is the only one: it is mounted on a sub-router in `routes/index.ts` that every money router hangs off, so a route added later is gated whether or not its author thought about it. That structural mounting is the actual decision — the defended failure mode is forgetting, and a per-route middleware someone must remember to add defends nothing. The 404-not-403 choice is not politeness: a 403 confirms the row is real, which turns the endpoint into a free directory of other people's business ids. `isolation.integration.test.ts` enumerates the endpoints from `@workspace/api-contract` rather than from a hand-written list — 100 gated endpoints today — so the sweep covers whatever is defined next year, and it carries a canary asserting the enumeration is non-empty so a refactor cannot make every assertion pass by testing nothing.

**2026-09-03 · The absent-header fallback resolves only when the user owns exactly one business. Zero and two-or-more both refuse.**
Why: the honest position is that a request which does not name its books cannot be answered, and the honest position would have broken every existing client on the day the header landed. The exception taken is not a guess: a user with exactly one business has exactly one candidate, so using it invents nothing. Two-or-more refuses because choosing for them writes money into the wrong books silently, which is the worst outcome available; zero refuses because there is nothing to open and the answer is a welcome screen, not a workspace nobody asked for. Both refusals carry `business_required`, which is the code the screens read to send the user to the businesses page. Measured: the whole existing frontend and all nine e2e steps pass unchanged through the fallback, so the server change shipped without a coordinated client change.

**2026-09-03 · A business's NAME and CURRENCY moved off `user_settings` and onto the business row. `ensureBusiness` is banned from the request path.**
Why: both describe one set of books, and an owner with a shop and a studio must be able to call them different things in different currencies — left on the account, the switcher would have shown the same label twice and priced both in one currency. `businesses` already had `name` and `base_currency`, so this was mostly a matter of reading the right row; `currency_symbol` joined them, and migration 0021 copies the account's values across (one-to-one, because the dropped unique index is what guaranteed each user had exactly one business to copy to). It declines to copy a `currency` of 'Rs', which is a symbol that had leaked into the code field on old rows, rather than carrying the mistake forward. Separately and more importantly, `ensureBusiness(userId)` used to run on EVERY request and create a business as a side effect of reading one — so a brand-new visitor silently acquired an empty workspace before anyone asked what they were building. It survives for seeders and fixtures, which legitimately own their user, and its header says so; the request path uses `businessOf(req)`, and `loadBusinessCapabilities` now takes the verified business rather than re-deriving one from a user id, because that re-derivation is the exact habit that made "the user's business" mean something when it no longer does.

**2026-09-03 · Settings split three ways: identity on `businesses`, per-books preferences on `business_settings`, and three fields left on `user_settings`.**
Why: the test for where a setting belongs is one question — would an owner want the same value in every one of their businesses? For a margin threshold, a cash buffer, an ad-attribution percentage or a budget the answer is plainly no, and leaving them on the account meant a second business silently reported against the first one's numbers, which is the kind of wrong that never announces itself. What survives on `user_settings` is `plan`, `locale`, `toasts_enabled` and the two Paddle columns, which were not touched: billing is per person and that was the one thing never in doubt. The floats came across unchanged — `cash_buffer`, `default_cost_price` and `default_selling_price` are `double precision`, which the money invariant forbids — because this migration is a MOVE and changing storage and location in the same step makes a reconciliation impossible to read. They are form prefills and a display threshold; no ledger figure is computed from them. Converting them to minor units is its own small piece of work. `budget_plan` came across too, against the original plan, because dropping it would have broken the Budget page before its replacement exists; per-business is already less wrong than per-account, and it leaves entirely when budgets become real tables.

**2026-09-03 · A connected account belongs to a business, not to a person. `unique(user_id, kind)` becomes `unique(business_id, kind)`.**
Why: this retires REWRITE_PLAN known-broken #10 — a seller could never connect a second Shopify store, because the unique index let one row exist per user per kind and the second connection overwrote the first. Keying on the business is not merely a bigger allowance: it is the only arrangement in which two stores' profit can be told apart, since the money a connector imports has to land in one set of books. The Shopify OAuth round-trip now carries the business inside its HMAC-signed state alongside the user, and `requireBusiness` is applied to the `/start` route specifically rather than router-wide, because the callback is reached by Shopify redirecting the browser and carries none of our headers. The callback re-checks ownership before writing a token: a signature proves the value was ours when it left, not that it is still theirs now. A reset keeps the connections — emptying the books is not the same as unplugging the shop, and making someone re-authorise Shopify to clear demo data would be a surprise.

**2026-09-03 · The migration copies, checks, then drops — and raises rather than deleting an orphaned connection.**
Why: drizzle-kit's generated version of the split dropped thirteen `user_settings` columns before anything read them, and added `integrations.business_id` as NOT NULL with no default to a table that has rows. Both were rewritten by hand. Two `DO` blocks make it reconcile-or-fail: one asserts a `business_settings` row exists for every business, the other refuses to continue if any integration belongs to a user with no business. That second one RAISES rather than deleting, and the choice is deliberate — the row holds an access token, and destroying credentials inside a migration is not a decision a migration gets to make quietly. Verified on the dev database: eight businesses each got exactly one settings row (five carrying their account's values, three taking defaults where no settings row had ever been written), and `user_settings` came out of it with seven columns.

**2026-09-03 · Switching business RELOADS the page. It is not a live swap, and that is the design.**
Why: seventy-four React Query keys in `api/hooks.ts` carry no business id, and the legacy `useStore` keeps its own arrays besides. Threading the id through every key would work until the next hook was written without it, and the failure it would produce is one business's figures rendered under another's name — the worst thing this app can do, and one nobody would catch by looking, because the numbers are all perfectly plausible. A reload makes a stale answer impossible by construction rather than by discipline. The cost is a flash on an action nobody performs ten times a day, and the same trade was already made by the dev account switcher, which has behaved this way since it was written. `switchBusiness` in `lib/currentBusiness.ts` is the one place that does it: write, `queryClient.clear()`, navigate.

**2026-09-03 · A brand-new account is offered sample data, not just an empty business.**
Why: a profit tool is impossible to judge empty. Every screen is an empty state, no chart can draw, and the honest reaction to a blank Profit Loop is "there is nothing here" — which is true, and tells the owner nothing about whether the product is worth their evening. The welcome screen therefore has two doors: name your business, or name it and fill it with the fixture seed that already existed for development. Verified end to end in the running app: a user who owned nothing went from the welcome form to a dashboard reading Rs 12,567 revenue and Rs 4,353 true profit in one click. The order inside `create()` matters and is commented — the business id is written to storage BEFORE the seed request, because that request reads its target from there.

**2026-09-03 · The businesses page prints each business's profit with that business's own currency symbol, using `formatCents` directly.**
Why: this is the one place the pattern CLAUDE.md bans is correct, so it is commented where it appears. The ban exists because pairing server cents with a symbol taken from SETTINGS once put a `$` in front of an unconverted rupee figure. Here both halves come off the same business row — the cents from that business's P&L, the symbol from that business's record — so they cannot disagree. `useFormatters()` would be the actual bug on this screen, because it is bound to whichever business is currently selected and would print every card in that one's money.

**2026-09-03 · A refused action says why, on the card. Found by driving the real app, not by a test.**
Why: the server correctly refuses to archive an owner's only business, and the first build of the page did nothing visible when it did — the request 400'd, the list did not change, and the only way to learn why was the network tab. A control that silently declines reads as broken software, which is the same class of defect as a screen answering a question it never got an answer to. The card now renders the server's own sentence ("This is your only business. Make another one before archiving this.") in amber, because colour means money and a refused action is not money lost. Worth recording how it was found: the typecheck passed, every suite was green, and the defect was only visible by clicking the button.

**2026-09-03 · OWED and OVERDUE are different things. Without an agreed date, nothing can be late.**
Why: this is the whole of `lib/domain/owed.ts` and the mistake it exists to prevent. The obvious implementation ages an invoice from the day it was raised and calls anything past thirty days late — which invents an agreement nobody made. Every unpaid sale would turn amber the moment it was entered, and an owner learns within a week to ignore the colour, at which point the screen has cost them the one signal it existed to give. So a transaction with no `due_date` is `no_due_date`: still owed, still ageing, still on the list, sorted by age among its peers — but never reported as late, because there is no promise for it to have broken. Lateness requires a date somebody chose. Sixteen unit tests hold the boundaries, including the one a timestamp subtraction gets wrong: a bill due yesterday is one day late at 00:05 and at 23:55 alike, so every comparison is by whole UTC calendar day rather than elapsed hours.

**2026-09-03 · The owed screen has no period filter, and says so on the page.**
Why: every other Money screen answers "how did this month go". This one answers "what is outstanding right now", and a debt does not stop existing because the header is showing August. Filtering by the global period would have hidden the oldest invoices — the only ones actually worth a phone call — and it would have done so silently, since the screen would still show a plausible total. The sentence is rendered at the top rather than left implicit precisely because the period picker sits directly above it and would otherwise look like it applies. The server read is not period-scoped either: `loadUnpaidTransactions` hangs off a partial index on `paid_at IS NULL`, so it stays small however long the ledger grows.

**2026-09-03 · Overdue is AMBER, not red.**
Why: colour in this app means money (DESIGN.md §2) — red is money lost. A late invoice is money still expected, and painting it red files it mentally with refunds and write-offs, which is the wrong alarm. Amber is already the app's signal for "something about this DATA needs attention", which is exactly what a missed date is. Every state also carries words in its tag, so the meaning never rests on the colour alone.

**2026-09-03 · Adding the column was not enough: the entry screens had to be able to SET a due date, or the whole overdue half was unreachable.**
Why: the plan for this stage said "migration adds due_date, nothing else", and taken literally that would have shipped a feature nobody could use — every row on the new screen would have read "No due date" for ever, because no screen could write one. Caught by driving the real app rather than by any test: the page rendered correctly against seeded data and the gap was invisible until there was a reason to type a date. Quick Add and the transaction drawer both gained the field, shown ONLY while the entry is unpaid — a due date on something already settled is a question about the past that changes nothing. The helper text states the rule in the owner's own terms: "with a date it can show as late; without one it just shows as outstanding — which is the truth when nothing was agreed."

**2026-09-03 · A project is a unit of WORK; an engagement is the terms of a RELATIONSHIP. They are different levels, so `projects` is a new table and `client_engagements` was not touched.**
Why: the tempting move was to rename engagements, since both carry an agreed amount and dates. It is wrong. An engagement is how you work with a client — one live at a time, an agreed fee, agreed hours. A project is a discrete piece of work, and one client on one engagement can run five of them; a production run has no client at all. Renaming would also have rippled through the twenty-six files that depend on engagements for no gain to the trades this stage exists for. The cost of the decision is two things on screen that look similar, and the mitigation is that they live in different places: engagement terms stay inside the person's record, projects have their own screen.

**2026-09-03 · Money reaches a project through the EXISTING target mechanism. No new money path, and the proof is that splitting and spreading worked on day one.**
Why: `transaction_lines.target_type` and `time_entries.target_type` already existed and already carried the machinery — splitting one bill by weights into exact shares, spread slices inheriting their line's target, cost snapshots frozen per line. Adding `project` as an enum value made all of it work at once, and the integration tests assert exactly that rather than taking it on trust: one bill split 60/40 across two sites reaches both and the parts sum to the bill; a machine bought for a site and spread over twelve months charges that site once, across the months it covers. Anything else — a project_costs table, a bespoke endpoint — would have been a second money path that every read in the app would have had to learn about separately.

**2026-09-03 · A SALE may name a project, and nothing else. Enforced by a database CHECK, not only by the service.**
Why: the ledger previously refused any target on a revenue line, on the sound argument that "who was this for" is a question about a cost — revenue already records who paid through `person_id`. That argument holds for clients and for revenue items and breaks for projects: a site that could show every cost it ran up but never the money it brought in is a worse lie than no figure at all. So exactly one target type is allowed on revenue, and the constraint lives on the table (`transaction_lines_revenue_target_check`) as well as in the service, because a write path added later would not think to ask.

**2026-09-03 · Project profit stops at contribution profit, and the screen says so in those words on every card.**
Why: CLAUDE.md forbids allocating fixed costs per item, and a project is item-level — head office rent does not belong to the Gulberg site in a ratio the software worked out, and an accountant asked to justify that ratio would refuse. What DOES land on a project is everything genuinely direct to it, including that site's own overheads; only company-wide costs stay out. The danger is not the arithmetic but the reading: a project showing Rs 1,950,000 has not put that in the bank. "Before your fixed running costs" is rendered under the figure on every card and again at the top of the page, because a number this size is exactly the one an owner will quote to somebody.

**2026-09-03 · The double-count the test caught: a capitalised purchase charged its project twice.**
Why worth recording: `lineSubtotal` does not know about spreading — that rule lives in `defersToSlices` inside the ladder — so the project totals counted the original purchase AND every monthly slice, and a Rs 240,000 machine arrived as Rs 480,000. It was written as a test before the code because it is the exact shape of mistake Stage 1's payables side had already made, and it failed on the first run. The fix is one `isCapitalised` check with the reasoning beside it. The general rule: any new read that sums transaction lines has to decide what it does about spreading, and the honest default for "what has this consumed" is accrual — the cash left in April, but the machine is used across the whole job.

**2026-09-03 · A router-level feature gate leaks onto every route mounted after it.**
Why: `router.use(requireFeature("projects"))` inside the projects router runs for EVERY request that reaches it, including ones matching nothing there that then fall through to the routers mounted afterwards — so integrations and the dev routes would have answered 403 for any business with projects switched off. Caught by reasoning about the mount rather than by a failing test, which is the uncomfortable part: nothing in the suite would have noticed. Scoped to the path prefix (`router.use("/projects", …)`), the same arrangement client profitability already used. The general rule for this codebase: `router.use(mw)` with no path is almost always wrong in a file that is one of several mounted on a shared parent.

**2026-09-03 · A refund carries the target of the line it reverses, and readers subtract it.**
Why: this closes a gap I shipped in Stage 2 and flagged rather than fixed. Refund lines named nobody, so anything reading by target never saw them — a site billed Rs 2,000,000 and refunded Rs 500,000 went on reporting Rs 2,000,000 earned, permanently, with no sign on screen that it was wrong. `createRefund` now copies `target_type` / `target_id` from the original line onto its reversal, and `services/project.ts` applies a sign of −1 to any transaction carrying an `adjustment_type`. The sign is not optional: refund lines inherit the ORIGINAL's direction, so a refunded sale produces "in" lines and a refunded cost produces "out" ones — without the sign, refunding a supplier's credit note would have made a site look MORE expensive. A chargeback fee has no original line and correctly inherits no target: it is a new cost, not a reversal. Two tests, one per direction.

**2026-09-04 - Budget actuals match by FOREIGN KEY, a label matches EXACTLY, and whatever matches nothing is shown.**
Why: the screen this replaces stored six fixed categories in a settings blob and found "actual spend" by searching expense names for words - "rent", "salary", "warehouse", "courier". Three faults, in rising order. It could not be extended, because the six were hardcoded. It matched wrongly, because "Rent" also claims "Equipment rental". And worst, money it failed to match simply VANISHED from the comparison: a business could be far over its real spending while every line on the page read comfortably under, and nothing on the screen would say so. So matching is on ids; a label is compared exactly rather than as a substring; and the unbudgeted figure is a headline tile, not a footnote. `budgetReconciles` states the property a test can assert - every rupee is either on a line or in that bucket - and the unbudgeted money counts toward the actual total, or the headline would understate exactly as the old one did.

**2026-09-04 - Most specific wins: an item beats a category, which beats a label.**
Why: a cost that is both "Cement" (the item) and "Materials" (the category) can only be counted once, and without an explicit order it would land in whichever budget line happened to be created first - so the owner's most precise statement would lose to their vaguest one at random. Two lines claiming the same thing is refused outright rather than resolved: counting the money twice overstates spending, and picking one silently leaves the other reading Rs 0 for no visible reason.

**2026-09-04 - The suggestion uses the MEDIAN month, with the mean shown beside it.**
Why: the mean is wrong for this job in a way that is easy to miss. One Rs 800,000 machine bought in March turns into a monthly equipment budget the business will never spend, and the owner either notices and distrusts the whole draft or does not notice and budgets nonsense. The median is a typical month. The mean is still returned and rendered when the two differ by more than a quarter, because the gap itself is information - on the demo business, Advertising showed a median of Rs 28,620 against an average of Rs 51,761, which is exactly the ad splurge the demo data contains. Suggestions cover catalogue items only: a one-off label ("Skip hire, March") happened once and is not a thing to budget for every month.

**2026-09-04 - Pace counts COMPLETE months, and a budget with no profit goal gets no pace at all.**
Why: the first was a real bug caught by a failing test - `monthsInSpan` counts both ends, which is right for a budget's length and wrong for elapsed time, so on 1 July the owner was being held to seven months when six had finished and told they were behind when they were exactly on pace. The second is a design choice: capping spending without saying what you want left over is a real and common way to use a budget, and the screen must not invent a target nobody set. Pacing is straight-line on purpose - apportioning a goal by last year's seasonality would be a forecast dressed as a plan, and a flat expectation is easy to argue with, which is the right property for a number that is telling someone off.

**2026-09-04 - Budget and Break-even are two screens now.**
Why: they shared a page and nothing else. Break-even was computed on the server from the real ledger and was sound; the budget half read a legacy in-browser bridge, guessed spending by name, and did its arithmetic in whole rupees in the browser - three CLAUDE.md violations on one screen. Splitting them let the bad half be deleted outright rather than repaired in place, and the good half moved across unchanged in substance. `finance.ts` lost `calculateBudgetAnalysis`, `calculateBudgetActuals` and `calculateBudgetUsage`; the `budgetPlan` settings blob is gone from the contract, the types, the store, the seed and the database (migration 0026).

**2026-09-04 - An advance spends nothing under accrual and everything under cash. It is the sibling of a spread purchase, not the same thing.**
Why: everything else in this ledger is a money event that is also an economic event - a sale earns, a bill costs. An advance is the one case where the two come apart in TIME rather than by a few days. Recorded as an ordinary payment it lands as a cost in a month where no work happened: that month reports a loss it did not have, and the month the work actually happens reports a profit it did not make. So the rule goes in `profit.ts` beside `defersToSlices`, as `defersUntilUsed`, and every breakdown, every category total and break-even inherit it for free. The two are checked with `||` and never summed, because a line marked both must defer once rather than twice into nothing. They differ in where "elsewhere" is: a spread cost has been incurred and belongs to the months it covers; an advance has not been incurred at all and belongs to whenever the bill finally arrives, which may be never. Verified in the running app: a Rs 200,000 advance and a Rs 500,000 bill gave accrual expenses of Rs 500,000 and cash expenses of Rs 200,000 - the money counted exactly once across the whole lifecycle.

**2026-09-04 - The mirror holds: a deposit TAKEN from a customer is not revenue.**
Why: it would have been easy to build only the paying half, since that is what the owner asked about. But the same flag on a revenue line is the same fact - cash has moved and nothing has been earned - and leaving it out would let a business book a year of deposits as a record year and only then discover the work still has to be done. One flag, both directions, and the settle path refuses to cross them: a customer's deposit does not pay a supplier, because netting two unrelated obligations against each other is not a saving.

**2026-09-04 - `payment_applications` is append-only and derived. `paid_at` stays the single answer to "is this settled".**
Why: the obvious alternative is a `remaining_cents` column on the bill, and it is wrong for the reason every stored balance is wrong - two things can then disagree, and the one nobody reads is the one that rots. Balances are computed: what is left of an advance is its amount less what has been drawn from it. When applications reach a bill's full amount the server stamps `paid_at`, so paid-ness has exactly one home and applications only ever explain HOW something was settled, never a second opinion on WHETHER. `applied_from_transaction_id` is nullable although nothing writes a null: a row with it null would be an ordinary cash part-payment, which is deliberately NOT built - the owner asked for advances, and building general part-payments under cover of them is how scope quietly doubles. The column is shaped that way anyway so part-payments would be this table plus a screen, not a migration and a second concept.

**2026-09-04 - The owed list nets off what an advance has already covered.**
Why: this was written as a test that documented the gap, and then the gap was closed rather than shipped. A Rs 500,000 bill part-settled by a Rs 200,000 advance is owed for Rs 300,000; showing its face value keeps chasing money that has already changed hands, which is the exact overstatement the advance was recorded to avoid. A bill covered in full has `paid_at` stamped and never reaches the list at all.

**2026-09-04 - Two shapes are refused at the ledger, because they are contradictions rather than preferences.**
Why: a cost recorded INSIDE a sale has already been incurred - it is that job's cost - so calling it an advance would defer money the job has already eaten. And a line cannot be both an advance and spread over months: both defer under accrual to different places, and a line claiming both is a statement nobody could act on when the bill arrives. Refusing at the write path rather than resolving silently is the same choice made for duplicate budget lines, and for the same reason: a wrong answer that looks ordinary is worse than an error.

**2026-09-04 - Waste is a slice of a cost already recorded, so it is never its own money row.**
Why: this is the one decision that had to be made before any code, because the obvious build is
wrong. Recording "Rs 3,000 of cement wasted" as an expense would count those bags twice - once
in the Rs 50,000 delivery, again as the loss - and a business tracking waste honestly would
appear to spend more than one that ignored it, which is precisely backwards as an incentive.
So `wasted_qty` sits on the line as information: no total moves, no rung of the ladder sees it,
and an integration test asserts exactly that. The figure is useful BECAUSE it is not new money -
it answers "how much of what I already spend is going nowhere", which the profit ladder cannot
answer at all.

**2026-09-04 - The waste rate covers only the purchases where waste was actually recorded.**
Why: a test I wrote expected 4% and the code returned 12%; the code was right. If ten cement
deliveries arrive and somebody checks two of them, the honest claim is "of the cement you
tracked, 12% went to waste" - counting the eight unchecked ones as zero waste assumes the
answer to the question being asked, and every rate on the report would drift down as the
business got lazier about recording. So the screen says "of what you tracked" in those words.
The headline share is deliberately the other way, over all spending, because it answers a
question about the whole business rather than about one material.

**2026-09-04 - There is no assets table, and there should not be.**
Why: a purchase spread over months already records everything an asset register holds - what it
was, what it cost, over how long, and therefore how much is left. Adding a table would create a
second copy of facts the ledger owns, and the two would disagree the first time a spread
purchase was voided or refunded. The Assets screen is a read. The one trap it has to avoid is
counting the same machine twice: the query takes originating transactions only, never the
monthly slices those transactions generate, and remaining value is split with
`allocateProportionally` so used plus left equals the purchase exactly.

**2026-09-05 - The demo is two businesses, not one.**
Why: the studio dataset was built before projects, retention, budgets, advances,
units, waste and plant existed, and none of them show up on an ecommerce shop —
so half the app could only be judged on hand-made fixtures. A builder exercises
the other half, and having two also means the multi-business restructure is
exercised every time anyone runs the seed rather than only when someone
remembers to test it. The wipe moved into the CLI as a consequence: a seeder that
wipes and then adopts "the user's business" cannot coexist with a second seeder,
so each one now creates its own.

**2026-09-05 - The wipe is checked by asking the database, not by listing tables.**
Why: forgetting to add a table to `wipeBusinessById` has now happened four times
— projects, payment applications, and budgets twice over — and every time the
failure landed somewhere far from the cause: a seed script that crashed, or a
test file whose `before` hook died on rows the PREVIOUS run left behind. Budgets
were the worst of them, because `budget.integration.test.ts` passed on a clean
database and failed on a re-run, so the suite looked green while shipping a wipe
that could not delete a business anyone had budgeted in. A test that lists the
tables it expects would have the same blind spot as the code it checks, so the
new one reads `information_schema` for every table carrying a `business_id` and
asserts all of them are empty afterwards. The next table is covered on the day it
is created.

**2026-09-05 - A line's category is the item's category when the line has none.**
Why: this was the budget's "Head office" row reading Rs 0.00 while Rs 3,130,405
was going out the door — the same shape of lie as the name-searching screen the
rewrite replaced, arrived at a different way. Entry forms do not ask for a
category when a catalogue item is picked, because the item already knows one, so
`line.category_id` is null on almost every real row and any reader that consults
it alone finds nothing. `read.ts` had this right already in `lineCategoryId`;
the budget had a second, wrong copy of the rule. The general lesson is the one
the profit ladder is built on: when two places answer the same question, export
the first one rather than writing the second.

**2026-09-05 - An asset is named by its label; waste is named by its item.**
Why: they look like the same decision and are opposite ones. An asset is a
specific thing an owner owns, so three rows reading "Plant purchase" are useless
where "Concrete mixer" and "Site pickup" are not. Waste is a total per material,
so taking the label would split "Cement — raft" and "Cement — plaster" into two
rows and hide that cement is the problem. The rule is what the row IS: one
object, or one kind of thing.

**2026-09-05 - A connector that cannot reach a real API says so. It never invents figures.**
Why: the code this replaces fabricated eight to twelve orders from a list of
sample customer names and called it a sync, and fourteen days of random daily ad
spend on top. It read as a working integration and was a demo in disguise — the
exact failure DECISIONS.md already names, a figure that looks meaningful and is
not, except here the owner would have been making decisions on invented revenue.
`live: false` on the registry entry and a plain sentence back is the honest
shape: Daraz can be connected, its figures have to be typed for now, and nothing
appears in the books that did not happen.

**2026-09-05 - The processor's fee is read, or it is nothing. It is never estimated.**
Why: CLAUDE.md's money-truth hierarchy says the processor owns the fee fact, and
the tempting shortcut is the source's `platform_fee_percent` — 2.9% and thirty
paisa, near enough. It is not near enough. A fee that is computed rather than
observed is a number the owner cannot reconcile against their Shopify statement,
and the first time they try, everything else the app says becomes suspect too.
So the fee comes from the order's own transactions, and a store not on Shopify
Payments gets no fee line at all. Missing is a state an owner can understand and
fix; wrong is not.

**2026-09-05 - A refund carries an external ref, exactly like the sale does.**
Why: Shopify re-delivers a webhook whenever it is unsure one landed, and the
sale was already safe — `unique(source_id, external_ref)` made a replay a no-op
at the database level. The refund had no such protection, so the same replay
would have posted the refund twice and handed the customer their money back
twice in the books. The fix is the same mechanism rather than a second one:
`createRefund` takes an `externalRef` and the existing index does the work.

**2026-09-05 - A connected store is a source, and the link is an id, not a name.**
Why: "a store, a marketplace account, a bank" is already the definition of a
source, so a connected account and a channel were always the same thing named
twice. The only real question was how they find each other. By name is the
obvious answer and the wrong one: an owner who renames the channel on screen
would silently start a second history for the same store, with half the orders
in each. `integrations.source_id` cannot drift.

**2026-09-05 - Test fixtures for the wipe have to be exhaustive, not representative.**
Why: the fifth instance of the wipe defect was found by the Shopify test rather
than by the test written the same week to prevent exactly it. The enumerating
query answers "did you forget a table", which is the more common mistake, but a
foreign key in the WRONG ORDER only raises when a row actually exists — so a
thin fixture makes the check silently weaker than it reads. Anything with a
foreign key into the business graph now goes into that fixture, and the comment
above it says so, because the next person will otherwise assume the enumeration
is doing all the work.

**2026-09-05 - A CSV import shares the integration dedupe key, and everything else it thinks about duplicates is a warning that is never stored.**
Why (CSV import design, `docs/superpowers/specs/2026-09-05-csv-import-design.md`):
imports need two different answers because files carry two different kinds of
identity. When the file HAS an order id, it goes to `external_ref` on the same
source, so `transactions_source_external_ref_uq` enforces uniqueness for good —
and that deliberately shares the namespace the schema comment reserves for
integrations, because a Shopify CSV imported today carries the ids the live
connector will send tomorrow. Sharing the key is what stops connecting the
integration later from doubling the year the owner already imported; only
`origin` distinguishes them, and it stays truthful. When the file has NO id — a
bank statement — the importer compares date, absolute amount, direction and the
normalized description, flags the matches, and unticks them. That comparison is
never written anywhere, because 2026-08-03 already recorded what a stored
content fingerprint does: correct a typo and the row no longer matches its own
past self, so it lands beside the row it was meant to replace. The match is
normalized-equal rather than fuzzy for the same reason a "similar" name is never
auto-applied to a timesheet — two identical charges on one day are ordinary and
legitimate, so the flag exists to be noticed, not to decide.

**2026-09-05 - A money import lands the rows it can read and reports the rest; the timesheet rule does not carry over.**
Why: the timesheet importer refuses the whole file over one unmatched name, and
that was right there — hours quietly missing look complete, and every client that
person touched then looks cheaper than they are. A money file is the opposite
shape. Bank exports carry footers, summary lines and blank amounts as a matter of
course, so whole-file refusal means one junk row blocks three hundred good ones,
every month, forever. The gap is also visible in a way the timesheet gap is not:
the check screen states all three counts before anything is written, and the
failed rows come back as a CSV with a `Problem` column to fix and re-upload. The
principle both rules serve is unchanged — nothing is invented and no shortfall is
hidden. Only the honest way to say it differs.

**2026-09-05 - Rows sharing an order id are ONE sale with many lines, and a disagreeing header field refuses the group.**
Why: platform exports are one row per ITEM, so the file the owner most wants to
import — a Shopify or Etsy order export — was the one the first draft handled
worst. Ungrouped, a three-item order became three orders in the ledger, and rows
two and three then collided on `unique(source_id, external_ref)` and were thrown
away as duplicates: a wrong order count AND lost lines, from the same mistake.
Grouping needs no new machinery, because header-plus-lines is what a transaction
already is. Two details are the whole of the risk. Order-level values take the
FIRST NON-BLANK value in the group rather than a sum, because exports either
repeat them on every row or put them on the first row only, and summing turns the
repeated case into triple the tax on a three-item order; where a file really is
per-item the matching screen asks once, rather than the parser guessing from
shape. And two rows carrying DIFFERENT non-blank values for the same header field
refuse the group instead of picking one — that disagreement means the file is not
what the mapping claims, and a silently chosen tax figure is a wrong order that
looks right forever. Grouping is off entirely without an id column, which is
correct for a bank statement, where nothing in the file says two rows belong
together.

**2026-09-11 - The import size cap counts BYTES, not characters, and sits at 3 MB.**
Why: it counted `String.length` — UTF-16 code units — while the hosting platform
counts UTF-8 bytes off the wire, and the two disagree by up to 3x on exactly the
files the cap is closest to refusing. A cap in the wrong unit has to be sized for
its worst case, so it had fallen to 1 MB and every Latin file paid for a
multiplier it never used: a real 60-column marketplace export runs over 800 bytes
a row, so the size cap began refusing files of about 1,300 rows — well inside the
5,000 the row cap allows, and not even a month for a shop doing 5,000 orders.
Counting bytes deletes the multiplier outright, because the thing measured
becomes the thing the platform counts, and the row cap goes back to being the
independent backstop it was meant to be. Measured rather than reasoned: a file
built to sit on the 3 MB cap to the byte, `JSON.stringify`d into the real commit
body with its mapping and 5,000 ticked-back-in keys, weighs 3.55 MB on the wire
in Latin and 3.47 MB in Japanese — the non-Latin case is the LIGHTER one, because
JSON escapes only quotes and line breaks and passes other scripts through as
their own bytes. Both clear the platform's 4.5 MB and sit under the 4 MB body
parser, which is now derived from the constant rather than written out a second
time in another file.

**2026-09-13 - The check screen refuses to import nothing, and commit sends the reading the owner was shown.**
Why: two ways the last screen before money could lie. A file with nothing ready

**2026-09-20 - The read model knows all FOUR target types, and a finished project still has a name.**

**2026-09-20 - What is owed is computed in one place, and it is not period-scoped.**

**2026-09-20 - A ladder's last rung is a result, so it carries a sign and never an operator.**

**2026-09-20 - A backup that cannot be restored is worse than no backup.**

**2026-09-20 - A date in a spreadsheet is a calendar day, so the browser sends the calendar.**

fingerprint had to move with it, because it reads those instants back into days

**2026-09-24 - The dashboard headline is a brand block, and the money figure on it carries a sign and a word instead of a colour.**
Why: the owner's reference design puts true profit large and white on a solid
orange card. That collides with the oldest rule in DESIGN.md — orange is the

The real cost was the money colour. Green-and-red is unreadable on a saturated

**2026-09-26 - An entry typed in dollars is converted into the business's own currency ON SAVE, and the dollars are remembered beside it. This revisits 2026-07-27 for typed entries.**
The owner asked to enter dollar amounts. The 2026-07-27 design (store foreign amounts, convert once at the read boundary) was built on the server but never reached a form, and wiring it up exposed three places it would have been wrong. (1) The transactions LIST keeps amounts as entered, and the legacy adapters (`ledgerAdapter`, `workbenchApi`) add those raw amounts together, so a $100 sale would have been summed as Rs 100. (2) A catalogue item's cost snapshot is built from components in BASE currency but was stored as if in the transaction's currency, so the read boundary would have multiplied a Rs 500 clay cost by the rate. (3) The refund modal sends amounts in the original's currency, so converting the list to base would have broken refunds instead.
Converting at the door removes all three at once: everything stored is base money, every screen stays correct without knowing currencies exist, catalogue costs are never reinterpreted, and refunds are entered in base. What was typed is kept in `entered_currency` / `entered_fx_rate` / `entered_amount_cents` (migration 0031) for display only; `currency` / `fx_rate_to_base` keep their old meaning for integrations. The conversion is `convertEntryToBase` in `lib/domain/enteredCurrency.ts`, called by the transactions route before the ledger or the preview sees the entry. Each amount rounds half-up to whole minor units. Every line must carry a typed price, because falling back to the catalogue price would read rupees as dollars.
Also: a named currency other than the business's own at a rate of 1 is now refused by `createTransaction` (that is how $100 would have become Rs 100). The rate box is pre-filled from open.er-api.com (free, no key, carries PKR; ECB-based feeds do not), asked at most twice a day and never remembered on failure. It is a suggestion only: the rate saved is the one the owner sends.
Not done yet: a dollar VIEW of totals. That is a display conversion, so it has to happen on the server beside the rates, never in the UI.
